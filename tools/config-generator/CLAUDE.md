# CLAUDE.md

Этот файл содержит рекомендации для Claude Code (claude.ai/code) по работе с кодом этого репозитория.

<a id="overview"></a>

## Обзор

Генератор документации конфигурации сервера NATS написан на Go. Он разбирает определения типов YAML и создаёт файлы Markdown для Docusaurus, включая структуру боковой навигации.

<a id="commands"></a>

## Команды

<a id="build-and-run-the-generator"></a>

### Сборка и запуск генератора
```bash
go run .
```

<a id="generate-markdown-documentation"></a>

### Генерация документации Markdown
```bash
go run . -markdown -dir <output-dir>
```

<a id="common-flags"></a>

### Основные параметры
- `-config <file>` — корневой файл YAML конфигурации; по умолчанию `config.yaml`
- `-types <dir>` — каталог типов; по умолчанию `types`
- `-markdown` — генерировать файлы Markdown для справочника
- `-dir <name>` — выходной каталог справочника; по умолчанию `reference`
- `-base <path>` — базовый путь URL справочника; по умолчанию `/reference/config`
- `-relative` — использовать относительные пути ссылок
- `-indexname <name>` — имя индексного файла каталога; по умолчанию `index.md`
- `-trimindex` — удалять имя индексного файла из пути URL
- `-sidebar <file>` — файл боковой навигации; по умолчанию `config-sidebar.json`

<a id="format-code"></a>

### Форматирование кода
```bash
go fmt ./...
```

<a id="architecture"></a>

## Архитектура

<a id="core-components"></a>

### Основные компоненты

**main.go** — точка входа, обрабатывающая параметры CLI и управляющая разбором и генерацией.

**parse.go** — парсер конфигурации:
- Загружает корневой файл YAML `config.yaml`
- Загружает определения типов из `types/`
- Рекурсивно раскрывает ссылки на определения типов
- Обрабатывает массивы `array(T)`, отображения `map(T)` и их вложенные сочетания
- Проверяет и нормализует определения свойств

**model.go** — модели данных структуры конфигурации:
- `Config` — контейнер конфигурации верхнего уровня
- `Section` — логическая группа свойств, например «Подключения» или «Кластеризация»
- `Property` — отдельное свойство конфигурации с типами, значениями по умолчанию, примерами и псевдонимами
- `TypeOption` — допустимый тип значения: примитив, массив, отображение или объект с вложенными разделами
- `Example` — пример документации с подписью и описанием

**markdown.go** — генератор документации Markdown:
- Создаёт иерархию каталогов с файлами `.md`
- Создаёт страницы свойств с таблицами типов, примерами и ссылками на вложенные свойства
- Генерирует боковую навигацию JSON для Docusaurus
- Поддерживает простые свойства и глубоко вложенные объекты

<a id="type-system"></a>

### Система типов

Генератор поддерживает гибкую систему типов, определяемую в YAML:

**Встроенные примитивные типы:**
- `string`, `integer`, `float`, `boolean`
- `duration` — формат Go time.Duration, например `10s`, `5m`
- `storage` — размер в байтах с единицами измерения, например `1MB`, `100K`

**Контейнерные типы:**
- `array(T)` — массив элементов типа T
- `map(T)` — отображение строковых ключей в значения типа T
- Вложенные сочетания, например `array(map(T))` и `map(array(T))`

**Пользовательские типы:**
Определяются в файлах `types/*.yaml`. Типы могут ссылаться на другие типы; ссылки рекурсивно раскрываются при разборе.

**Поддержка нескольких типов:**
Свойства могут принимать значения нескольких типов. Например, `jetstream` может быть логическим значением, строковым перечислением или объектом.

<a id="configuration-flow"></a>

### Обработка конфигурации

1. **Разбор** (`parse.go`):
   - Загрузить корневой `config.yaml` с разделами и свойствами
   - Загрузить все определения из `types/*.yaml`
   - Проиндексировать типы по имени для разрешения ссылок
   - Рекурсивно раскрыть определения типов каждого свойства
   - Построить полную структуру `Config` со всеми разрешёнными типами

2. **Генерация** (`markdown.go`):
   - Создать структуру выходных каталогов по вложенным свойствам
   - Создать подкаталог для каждого свойства с вложенными объектами
   - Создать `index.md` для свойств с дочерними элементами
   - Создать `<property>.md` для конечных свойств
   - Построить JSON боковой навигации с вложенными категориями
   - Связать вложенные свойства относительными или абсолютными путями

<a id="type-definition-files"></a>

### Файлы определений типов

Находятся в каталоге `types/` и сгруппированы по назначению:
- `shared.yaml` — общие типы: `host`, `listen`, `enable-disable`
- `accounts.yaml` — настройки учётных записей и пользователей
- `auth.yaml` — авторизация и аутентификация
- `cluster.yaml` — кластеризация серверов
- `gateway.yaml` — шлюзовые соединения между кластерами
- `jetstream.yaml` — механизм постоянного хранения JetStream
- `leafnode.yaml` — соединения листовых узлов
- `mappings.yaml` — сопоставление и преобразование тем
- `mqtt.yaml` — интерфейс протокола MQTT
- `ocsp.yaml` — настройки OCSP stapling
- `resolver.yaml` — настройки resolver учётных записей
- `tls.yaml` — настройки TLS/SSL
- `websocket.yaml` — интерфейс WebSocket

<a id="property-metadata"></a>

### Метаданные свойств

Свойства поддерживают следующие метаданные для документации:
- `description` — подробное объяснение
- `deprecation` — уведомление об устаревании с рекомендациями по переходу
- `default` — значение по умолчанию
- `aliases` — альтернативные имена свойства
- `reloadable` — возможность применить изменения без перезапуска. Значения совпадают со столбцами `reloadable-audit.tsv`, что позволяет напрямую сопоставлять и проверять данные:

  | Значение | Метка | Значение метки |
  | :--- | :--- | :--- |
  | не задано | отсутствует | никто не проверял; значение может наследоваться |
  | `reloadable` | Перезагрузка без перезапуска | работающий сервер применяет изменение |
  | `not-reloadable` | Требуется перезапуск | перезагрузка отклоняется; `diffOptions` останавливается на первом неподдерживаемом поле, поэтому вся перезагрузка завершается неудачей |
  | `noop` | Игнорируется до перезапуска | перезагрузка проходит успешно, но новое значение игнорируется; оператор не получает об этом уведомления |

  Значения по умолчанию нет: отсутствие значения никогда не отображается как `reloadable`. Неизвестное значение приводит к ошибке сборки.
- `reloadable_note` — ограничения перезагрузки. Показываются под меткой либо отдельно, если `reloadable` не задан. В сводных таблицах родительских свойств обозначаются звёздочкой (`Yes*` / `No*`).
- `examples` — примеры кода с подписями и описаниями
- `version` — версия сервера, в которой появилось свойство

- `version` — версия сервера, в которой появилось свойство, например `"2.12"`. В документации более ранних версий свойство полностью отсутствует; в новых появляется метка `<Since />`, кроме случаев, когда значение не новее самой старой публикуемой версии. Всегда заключайте версию в кавычки: без них `2.10` выглядит как число с плавающей точкой.
- `removed` — версия сервера, из которой свойство удалено. Начиная с неё оно не отображается.
- `versions` — отображение версий в точечные переопределения, применяемые при отображении соответствующей версии. Ключ может перечислять несколько версий: `"2.11, 2.12"`. Переопределять разрешено только `reloadable`, `reloadable_note`, `default`, `description`, `deprecation` и `choices`; `type` и дочерние свойства менять нельзя. **Исходное значение используется для любой неуказанной версии**, поэтому новая младшая версия сервера без изменений не требует правки спецификации. Версия, отсутствующая в `-known`, вызывает ошибку сборки: опечатка обнаруживается явно.

<a id="inheritance-and-per-context-overrides"></a>

### Наследование и переопределения по контексту

Метаданные _типа_ наследуются каждым ссылающимся на него свойством, только если само свойство не задаёт поле: значение в месте ссылки всегда имеет приоритет. Наследуются `default`, `aliases`, `url`, `reloadable`, `reloadable_note`, `version`, `removed`. Не наследуются `description`, `deprecation`, `examples`: они содержат конкретные значения и относятся к месту использования. Наследование работает только тогда, когда свойство разрешается ровно в один тип; при нескольких типах нельзя однозначно выбрать источник.

Оценки перезагрузки не распространяются на дочерние свойства. Метка `not-reloadable` у блока не запрещает менять все его вложенные ключи: измерения показали, что их поведение отличается от родительского и друг от друга.

- `omit` — исключает свойство из отображаемого дерева в одном месте ссылки. Общий тип может объявлять ключ, который сервер запрещает в конкретном контексте: `network-authorization` объявляет `users`, но cluster и gateway выдают ошибку «does not allow multiple users» (`opts.go:1942`, `:2185`) и не запускаются. Документирование такого ключа направило бы читателя к неработающей конфигурации, поэтому страница удаляется. Если `omit: true` указан для имени, которого нет в исходном типе, сборка завершается ошибкой; иначе вместо удаления возникла бы несуществующая страница.

Если общий тип требует разных значений в разных контекстах, переопределяйте отдельные дочерние свойства в месте ссылки:

```yaml
      tls:
        type: tls
        properties:          # Объединяется ПО ИМЕНИ с дочерними свойствами типа
          timeout:
            reloadable: not-reloadable
          pinned_certs:
            reloadable: reloadable
```

Переопределения могут быть вложенными. Запись без имени типа, содержащая только `properties:`, объединяется с исходным определением, поэтому исправление может затронуть и свойство следующего уровня:

```yaml
      authorization:
        type: network-authorization
        properties:
          default_permissions:
            properties:
              allow_responses:
                reloadable: noop
```

Узел, в котором задано переопределение, не должен совместно использоваться другими отображаемыми путями, иначе изменение затронет все эти контексты.

Используйте этот механизм вместо дублирования типов. Аудит показал, что только у `tls` свойство `timeout` имеет четыре разных варианта поведения в семи контекстах. Отдельный тип для каждого контекста потребовал бы около пятнадцати новых имён с повторением полного списка свойств.

<a id="rendering-commands"></a>

### Команды отображения

```bash
go run . -markdown -dir out -version 2.12 -known 2.11,2.12,2.14   # Одна версия
go run . -audit    -version 2.14 -known 2.11,2.12,2.14            # TSV с путём, типом и оценкой перезагрузки
go run . -markdown -dir out -strict                               # Завершить с ошибкой, если отсутствует хотя бы одна оценка
go test ./...
```

Параметр `-audit` упрощает заполнение данных: результаты проверки привязаны к пути отображаемой страницы, а спецификация описывается через типы. Объединение выгрузки с `reloadable-audit.tsv` показывает общие типы с противоречащими оценками, которым нужны переопределения по контексту. Каждый запуск выводит покрытие перезагрузки в stderr; `-strict` превращает пробелы в ненулевой код выхода и должен оставаться выключенным до завершения заполнения.

Не считайте `hot-reload-opts.md` авторитетным источником. Проверка по nats-server v2.11.17 / v2.12.12 / v2.14.3 обнаружила ошибки в обе стороны. Оценки отдельных ключей находятся в `reloadable-audit.md` в корне репозитория. Эти оценки перенесены в спецификацию: каждая отображаемая страница соответствует аудиту для всех трёх версий, и проверка `-strict` проходит.

Сам аудит тоже требует проверки: он выполнен по другим тегам, чем используемые документацией. Проверялись v2.11.17 / v2.12.12 / v2.14.3, а `scripts/doc-versions.json` закрепляет v2.11.9 / v2.12.4 / v2.14.0; поведение перезагрузки меняется и внутри младшей версии. Известный пример — `gateway.tls.pinned_certs`: аудит считает его перезагружаемым во всех трёх версиях, что верно для проверенных тегов, но неверно для тегов документации 2.11 и 2.12, где изменение прерывает всю перезагрузку. Для этого ключа здесь заданы ограничения по версиям, намеренно отличающиеся от аудита. Прежде чем доверять строке, повторно изучите исходный код закреплённого тега; процедура описана в навыке `config-reload-audit`.

При записи TSV 34 строки ограничений были жёстко обрезаны до 160 символов. Эти ключи повторно проверены по исходному коду сервера, а примечания переписаны вручную. Обрезанные строки TSV всё ещё непригодны: проверяйте длину, прежде чем копировать этот столбец.

58 ключей, которые аудит счёл отсутствующими во всех версиях, проверены по `nats-server` и удалены из спецификации. Это `authorization.users` и `.token` в cluster и gateway — ошибки конфигурации, препятствующие запуску; ключи leafnode `authorization`, не поддерживаемые `parseLeafAuthorization`/`parseLeafUsers`; `verify_cert_and_check_known_urls` в обоих блоках TLS листового узла; а также `websocket.jwt_token`, который был опечаткой вместо `jwt_cookie` и переименован.

<a id="key-design-patterns"></a>

## Основные принципы проектирования

**Разрешение типов:** ссылки рекурсивно раскрываются до конечных вариантов: примитивов, перечислений или объектов с явно заданными свойствами. Типы, на которые ссылаются, сами могут иметь несколько вариантов.

**Иерархическая документация:** свойства объектных типов создают собственные страницы с вложенными свойствами, образуя дерево для навигации.

**Генерация боковой навигации:** структура JSON повторяет иерархию документации: свойства с дочерними элементами образуют категории, конечные свойства — прямые ссылки.

**Гибкие ссылки:** поддерживаются относительные ссылки для локальной разработки и абсолютные пути для опубликованного сайта, с необязательным удалением имени индексного файла.
