# Отказ узла {#surviving-node-loss}

Пока использовался один локальный nats-server: удобно для обучения, недостаточно рабочим заказам.

Потеря диска, падение или перезапуск этой машины угрожают ORDERS. Рассмотрим защиту, которую нужно включить явно.

Два понятия: **реплики** — число копий — и **надёжность хранения** — сохранение копии после перезапуска.

## Реплики {#replicas}

`nats stream info ORDERS` всё ещё показывает `Replicas: 1` со страницы [первого потока](/learn/jetstream/your-first-stream).

**R=1** — один сервер, одна копия журнала.

Отказоустойчивости нет: потеря единственной копии означает потерю сообщений и позиций потребителей. Для ноутбука допустимо, для эксплуатации рискованно.

**R=3** размещает три копии на трёх серверах и переживает отказ одного. Это минимальная рекомендуемая рабочая конфигурация.

Оставшиеся два — **большинство** из трёх, достаточное для чтения и записи без ручного восстановления и потери подтверждённых данных.

Порядок согласуется большинством по алгоритму Raft. Пока доступно больше половины, группа работает. Подробности — в [Кластеризации и репликации](/learn/clustering).

**R=5** выдерживает два одновременных отказа; пять — максимум. Обычно используют R=3, R=5 — для состояния, которое нельзя пересоздать.

## Лидер потока {#the-stream-has-a-leader}

Реплики выбирают **лидера**, остальные — **ведомые**.

Лидер назначает номер, сохраняет запись и возвращает PubAck лишь после наличия у большинства. Поэтому подтверждённое сообщение R=3 переживает отказ любого одного узла.

У потребителей собственные лидеры на репликах потока, поэтому доставка распределена. [Direct Get](/learn/jetstream/get-direct) может обслужить любая реплика. Различие лидеров потока, потребителей и метаданных объясняет [Кластеризация](/learn/clustering).

При отказе лидера оставшиеся автоматически выбирают нового. Запись кратко приостанавливается, затем продолжается; сообщения с PubAck уже имелись у большинства.

<div class="nats-flow" data-scenario="leaderFailoverAnimated" data-width="780" data-height="320"></div>

Отправленная, но ещё не подтверждённая публикация могла не дойти до большинства. Клиент не получает PubAck и должен повторить. Гарантия относится к подтверждённым записям, а не к находившимся в пути.

При потере двух из трёх большинства нет: лидер не выбирается, запись ждёт возврата реплик. Остановка предпочтительнее небезопасного подтверждения.

## Надёжность хранения {#storage-durability}

Количество задаёт копии, тип хранения — переживание перезапуска.

`Storage: File` — стандарт: данные на диске читаются после перезапуска.

**Memory** быстрее, но копия в RAM теряется при рестарте. Подходит восстанавливаемым данным, не журналу заказов.

Тип задаётся всему потоку: нельзя смешать одну файловую и две памяти в R=3.

R=3 File сочетает отказоустойчивость и дисковые копии. R=3 Memory переживает один отказ, но не одновременный перезапуск всей группы.

Даже File не синхронизирует каждую запись немедленно: после PubAck данные могут оставаться в кеше ОС. Граница гарантии разобрана в [Репликации и R=3](/learn/clustering/replication-and-r3).

## Репликация потребителей {#consumers-replicate-too}

Позиции и неподтверждённые сообщения shipping тоже реплицируются, сохраняя состояние пула при отказе.

Долговременный потребитель наследует число реплик потока. На Limits можно задать меньше, но не больше. На Interest и WorkQueue оно обязано совпадать.

Все настройки — в [Конфигурации потребителя](/reference/jetstream/api/consumer/create). Здесь наследуется стандарт.

## Выгоды и стоимость реплик {#what-replicas-buy-and-what-they-cost}

Увеличение копий повышает надёжность и нагрузку, но не масштабирует пропускную способность записи.

**Реплики потока R=3/R=5:**

- Переживают отказы узлов.
- Распределяют чтение через разных лидеров потребителей и [Direct Get](/learn/jetstream/get-direct).
- Требуют полный журнал на каждой и передачу записи большинству перед PubAck. R=3 — примерно втрое больше хранения и трафика записи R=1.
- Не распределяют запись: лидер один, дополнительные копии скорее снижают её пиковую скорость.

**Реплики потребителя:**

- Сохраняют позицию и ожидающие ack при смене лидера.
- Не ускоряют доставку: работает один лидер, ведомые готовы заменить его и добавляют нагрузку.

Для производительности нужны другие средства:

- Больше [обработчиков](/learn/jetstream/worker-pool).
- Разделение тем между потоками для обхода одного лидера — [Сопоставление тем](/learn/jetstream/subject-mapping).
- Размещение потоков по серверам — [Кластеризация](/learn/clustering).

## Типичные ошибки {#pitfalls}

Ошибки, проявляющиеся при первом отказе:

**Доверие R=1.** Без второй копии потерянный диск уничтожает ORDERS и позиции. До реальных заказов проверьте количество, не предполагайте R=3 автоматически.

**Чётное количество.** R=2 не выдерживает один отказ, R=4 выдерживает один, как R=3, за цену четвёртой копии. Выбирайте R=3 или R=5, максимум пять.

**Выводы по одному серверу.** Локальный успех не проверяет отказоустойчивость. Продемонстрируйте выборы и восстановление на реальном кластере по [главе кластеризации](/learn/clustering).

## Что уже готово {#where-you-are}

Локальный ORDERS не менялся: R=1 File на одном сервере.

Изменилась модель:

- R=1 — единая точка отказа.
- R=3 — три копии и устойчивость к одному отказу.
- File переживает рестарт, Memory нет.
- Записи идут лидеру, заменяемому автоматически.
- Реплики — надёжность, а производительность дают обработчики и разбиение.
