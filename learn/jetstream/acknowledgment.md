# Виды подтверждений и повторная доставка {#ack-responses-and-redelivery}

`shipping` создан с `AckPolicy=explicit`: каждое доставленное сообщение требует ответа и не считается завершённым без клиента.

Разберём ack, nak, term («прекратить попытки»), in-progress («ещё работаю») и серверные настройки задержавшихся или отсутствующих ответов.

## Почему сервер ждёт ответа {#why-the-server-waits-for-an-answer}

После доставки сообщение остаётся в обработке: сервер учитывает его в списке ожидающих и запускает таймер.

Без ответа он предполагает остановку обработчика и повторяет доставку. У цикла две части.

Первая — таймер AckWait, по умолчанию 30 секунд.

Вторая — один из четырёх ответов.

## Четыре ответа {#the-four-responses}

Клиент отвечает следующими способами.

**ack** — успех обработки. Сервер убирает сообщение из ожидающих и больше не выдаёт этому потребителю.

**nak** — отрицательное подтверждение: обработка не удалась, нужна новая попытка. Обычный nak требует немедленного повтора; можно задать задержку, как показано [ниже](#negative-ack-with-a-delay).

**term** — прекратить попытки: сообщение никогда не удастся обработать. Как при ack, оно исключается из ожидающих, хотя работа не выполнена.

**in-progress** — работа продолжается. Это не окончательный ответ: он сбрасывает AckWait, предотвращая повтор во время долгой обработки. Позже нужен итоговый ответ.

Ack, nak и term завершают доставку; in-progress продлевает таймер.

## Отрицательное подтверждение с задержкой {#negative-ack-with-a-delay}

Немедленный повтор обычного nak редко полезен.

Временный сбой — недоступный сервис, блокировка строки или превышение частоты запросов — при мгновенном повторе обычно возникает снова и создаёт непрерывный цикл.

Передайте задержку в nak: сервер подождёт перед следующей выдачей. Это вызов библиотеки; CLI `--nak` задаёт только немедленный повтор, поэтому вкладки CLI здесь нет. Для интервалов тайм-аутов через CLI настройте [backoff](#backoff-a-growing-delay-between-attempts).

<div class="nats-example" data-type="learn-jetstream-acknowledgment-nakWithDelay" data-languages="js,go,python,java,rust,csharp,c"></div>

Сообщение возвращается потребителю, не обязательно тому же обработчику [пула](/learn/jetstream/worker-pool). Каждый nak также создаёт уведомление `$JS.EVENT.ADVISORY.CONSUMER.MSG_NAKED.ORDERS.shipping`; поля — в [Справочнике → Уведомление nak](/reference/jetstream/advisory/nak).

Задержку nak клиент выбирает для одной попытки. **Backoff** автоматически задаёт интервалы повторов, но только по истечении AckWait: обычный nak он не замедляет.

## Term: необрабатываемое сообщение {#term-the-poison-message-path}

Повреждённая нагрузка или невыполнимая проверка — постоянная ошибка. Повторы лишь расходуют попытки.

Ответ term сразу убирает сообщение из ожидающих независимо от остатка MaxDeliver.

<div class="nats-example" data-type="learn-jetstream-acknowledgment-termPoison" data-languages="cli,js,go,python,java,rust,csharp,c"></div>

**После term** сообщение больше не выдаётся этому потребителю, а граница подтверждения проходит его. При стандартной `Limits` данные остаются другим потребителям до ограничений хранения. При `WorkQueue` или `Interest` term удаляет сообщение так же, как ack; см. [Политики хранения](/learn/jetstream/retention-policies).

Поскольку работа не выполнена, сервер публикует **уведомление о прекращении** в `$JS.EVENT.ADVISORY.CONSUMER.MSG_TERMINATED.ORDERS.shipping`: номера потока и потребителя, число доставок и необязательная причина. Отслеживайте его, чтобы `order_id` не исчез бесследно. Поля — в [Справочнике → Прекращение доставки](/reference/jetstream/advisory/terminated).

Используйте term только при уверенности, что будущие попытки не помогут. При сомнении — nak с задержкой и пределом доставок.

## Настройки сервера {#the-server-controls}

Четырём ответам клиента соответствуют две настройки потребителя.

**AckWait** — время ожидания ack, nak или in-progress. При истечении сервер повторяет доставку. По умолчанию 30 секунд; настройте по длительности работы.

**MaxDeliver** — максимальное число выдач сообщения. Стандартное `-1` означает отсутствие предела и потенциально бесконечные повторы.

AckWait обрабатывает отсутствие ответа, MaxDeliver ограничивает повторяющиеся неудачи и nak.

Тайм-аут и nak приводят к повтору, но расписание backoff действует лишь на тайм-аут. Для задержки nak укажите её в самом ответе.

Задайте оба параметра через `nats consumer edit`:


С `--max-deliver=5` после пяти неудачных выдач доставка прекращается. Term позволяет коду завершить её раньше.

## Backoff: растущая задержка попыток {#backoff-a-growing-delay-between-attempts}

Обычный AckWait одинаков для всех повторов. Backoff задаёт рост.

Список интервалов может ждать секунду до второй доставки, пять до третьей, 30 до четвёртой.

CLI строит список из диапазона:

```bash
nats consumer edit ORDERS shipping --backoff=linear --backoff-steps=5 --backoff-min=1s --backoff-max=30s
```

Если элементов меньше, чем разрешает MaxDeliver, последний интервал используется для оставшихся попыток.

Backoff заменяет AckWait: первый элемент становится сроком первой доставки. `--backoff-min=1s` переопределяет прежние 10 секунд одной секундой. Минимум должен покрывать нормальную обработку, иначе повтор начнётся ещё во время работы.

Все флаги перечислены в `nats consumer edit --help`. Здесь используется линейный диапазон.

## Другие политики подтверждения {#ack-policy-the-other-values}

Кроме `explicit` у AckPolicy есть ещё три значения.

`explicit` подтверждает каждое сообщение и подходит работе без допустимых потерь. `none` считает сообщение завершённым сразу после доставки: нет ожидающих, Ack Wait и повторов. `all` подтверждает также все предыдущие: дешевле, но требует строгого порядка. Без `MaxAckPending=1`, как показано в [Доставке и подтверждении](/learn/jetstream/delivery-and-acknowledgment), ack номера 10 может незаметно завершить неудачный 7, ожидающий повтора. `flow_control` используется сервером для push-потребителей долговременных зеркал и источников: подтверждения идут с управлением потоком и ведут себя как `all`. Для `shipping` его не задают.

Политики перечислены в [Конфигурации потребителя](/reference/jetstream/api/consumer/create). Здесь используется `explicit`.

## Типичные ошибки {#pitfalls}

Большинство ловушек — взаимодействия простых настроек.

**Nak без задержки повторяет сразу.** Временный сбой зацикливает обработчик на одном сообщении. Используйте задержку nak: backoff потребителя влияет только на тайм-ауты.

**Неисправимое сообщение без term расходует все попытки.** Если будущий успех невозможен, немедленно завершайте term, не задерживая следующие сообщения.

**MaxDeliver не создаёт очередь недоставленных сообщений.** После предела обычная выдача прекращается, данные остаются в потоке, но shipping явно об этом не сообщает. Встроенной dead-letter-очереди нет. Подпишитесь на `$JS.EVENT.ADVISORY.CONSUMER.MAX_DELIVERIES.ORDERS.shipping`; [схема уведомления](/reference/jetstream/advisory/max-deliver) позволяет обнаружить потерянный для обработки `order_id`:

**AckWait короче работы создаёт двойную обработку.** При отсутствии in-progress сервер выдаст ещё обрабатываемое сообщение второму клиенту. Увеличьте AckWait для медленного случая или регулярно сбрасывайте таймер in-progress.
