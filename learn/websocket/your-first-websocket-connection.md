# Первое соединение WebSocket {#your-first-websocket-connection}

Складской панели Acme в браузере нужны поступающие сообщения `orders.>`. Сделаем это в два этапа: откроем слушатель WebSocket, затем подключим сначала CLI `nats`, проверяя слушатель без HTML, а после — саму страницу.

## Открытие слушателя {#open-the-listener}

Блок `websocket {}` имеет собственные хост и порт, отдельные от клиентского 4222:

```conf
# ws-dev.conf — one server, two listeners
listen: 127.0.0.1:4222

websocket {
  listen: 127.0.0.1:8080
  no_tls: true
}
```

`no_tls: true` позволяет запустить пример на локальной машине. Иначе TLS обязателен: без блока `tls {}` и этого флага сервер откажется запускаться:

```
nats-server: websocket requires TLS configuration
```

Эксплуатационная конфигурация рассматривается в разделе [TLS и прокси](/learn/websocket/tls-and-proxies). Пока используется открытое соединение на localhost.

Запустите сервер:

```bash
nats-server -c ws-dev.conf
```

Две строки журнала подтверждают состояние:

```
[INF] Listening for websocket clients on ws://127.0.0.1:8080
[WRN] Websocket not configured with TLS. DO NOT USE IN PRODUCTION!
```

Предупреждение верно: клиент, передающий bearer-токен через `ws://`, отправляет его открытым текстом.

### Укажите порт, иначе слушателя не будет {#set-the-port-or-theres-no-listener}

Порта по умолчанию нет. Если блок его не содержит, сервер запускается, ничего не сообщает о WebSocket и слушает только 4222:

```conf
websocket {
  no_tls: true
}
```

```
[INF] Listening for client connections on 127.0.0.1:4222
```

Нет ошибки, предупреждения или слушателя. Если клиент не подключается, а журнал вообще не упоминает WebSocket, причина в этом. Задайте `port` либо `listen`, определяющий хост и порт вместе.

## Подключение CLI через ws {#connect-the-cli-over-ws}

CLI `nats` основан на клиенте Go, принимающем `ws://`. Подпишитесь через слушатель WebSocket:

```bash
nats -s ws://127.0.0.1:8080 sub "orders.>"
```

```
16:15:11 Subscribing on orders.>
```

Во втором терминале опубликуйте через обычный клиентский порт:

```bash
nats -s nats://127.0.0.1:4222 pub orders.new "ord_8w2k"
```

Подписчик получает сообщение:

```
[#1] Received on "orders.new"
ord_8w2k
```

Издатель на 4222 и подписчик на 8080 используют одну тему одного сервера. Им не нужно знать транспорт другой стороны. Нет моста или отдельного пространства тем: WebSocket — ещё один вход в тот же сервер.

## Что меняет транспорт {#what-the-transport-changes}

Только URL. Поддерживающие WebSocket клиенты используют прежний список серверов с другой схемой:

| Клиент | URL сервера |
|---|---|
| CLI `nats` | `nats -s ws://127.0.0.1:8080` |
| Go | `nats.Connect("ws://127.0.0.1:8080")` |
| JavaScript/TypeScript | `wsconnect({ servers: "ws://127.0.0.1:8080" })` |
| Python | `nats.client.connect("ws://127.0.0.1:8080")` — требуется `pip install nats-core[websocket]` |
| Java | `Nats.connect("ws://127.0.0.1:8080")` |
| Rust | `async_nats::connect("ws://127.0.0.1:8080")` |
| C#/.NET | `new NatsOpts { Url = "ws://127.0.0.1:8080" }` |

Python требует не только URL. В `nats-core` WebSocket вынесен в необязательное дополнение: обычный `pip install nats-core` не открывает `ws://`, установите `nats-core[websocket]`. Этот новый клиент требует Python 3.13 или новее.

Если у слушателя есть сертификат, используйте `wss://`. Темы, группы очередей, запросы и ответы, JetStream и заголовки ведут себя как при `nats://`: над транспортом работает тот же протокол.

## Подключение браузера {#connect-the-browser}

Теперь панель. Сохраните единственный файл без этапа сборки как `dashboard.html` и откройте:

```html
<!doctype html>
<title>Acme orders</title>
<ul id="orders"></ul>

<script type="module">
  import { wsconnect } from "https://esm.sh/@nats-io/nats-core";

  const nc = await wsconnect({ servers: "ws://127.0.0.1:8080" });
  const list = document.getElementById("orders");

  for await (const m of nc.subscribe("orders.>")) {
    const li = document.createElement("li");
    li.textContent = `${m.subject} — ${m.string()}`;
    list.append(li);
  }
</script>
```

Снова опубликуйте через CLI:

```bash
nats -s nats://127.0.0.1:4222 pub orders.new "ord_2zr9"
```

Строка появляется на странице. Это обычная подписка NATS, а `orders.>` — обычная подстановка.

Файл работает прямо с диска, поскольку сервер по умолчанию принимает любой источник страницы. После включения проверки источника это меняется; см. [Браузеры и источники](/learn/websocket/browsers-and-origins).

### Всегда явно задавайте порт в nats.js {#always-give-natsjs-an-explicit-port}

Если порт не указан, `wsconnect()` подставляет его самостоятельно, и это никогда не 4222:

| Что передано | Куда подключается |
|---|---|
| `ws://host:8080` | `ws://host:8080` |
| `ws://host` | `ws://host:80` |
| `wss://host` | `wss://host:443` |
| `host` | `wss://host:443` |
| `nats://host:4222` | `ws://host:4222` |

Одно имя хоста означает TLS на 443, а `ws://` без порта — 80. Скорее всего, слушатель находится не там, и ошибка выглядит как недоступность сервера. Последняя строка — отдельная ловушка: порт сохраняется, схема меняется, и WebSocket-рукопожатие отправляется обычному клиентскому порту. Всегда указывайте схему и порт.

## Двоичные кадры: кадр не равен сообщению {#binary-frames-and-why-a-frame-isnt-a-message}

Важны две детали протокола: одна для всех, другая для разработчиков клиентских библиотек.

NATS использует **двоичные** кадры данных WebSocket. Сервер всегда отправляет двоичные кадры и ожидает того же от клиентов.

Для разработчика библиотеки: кадр не обязан содержать целое сообщение NATS и обычно не содержит. В нём может быть часть `MSG` или несколько сообщений. Передавайте полезную нагрузку анализатору, умеющему работать с частичным протоколом, не приписывая границам кадров смысл. Требования описаны в [справочнике клиентского протокола](/reference/protocols/client).

## Подводные камни {#pitfalls}

**Неверный слушатель.** `nats://` на 8080 и `ws://` на 4222 не работают, а ошибка не называет истинную причину. Клиентам WebSocket нужен порт `websocket {}`, остальным — клиентский порт.

**Блок `websocket {}` без порта.** Сервер работает, слушателя нет; значения по умолчанию не существует. Проверьте журнал на `Listening for websocket clients`: отсутствие строки означает, что порт не задан.

**Блок `websocket {}` без `tls {}` и `no_tls: true`.** TLS обязателен по умолчанию, поэтому запуск завершается сообщением `websocket requires TLS configuration`.

**URL без явного порта.** Nats.js подставляет порт, но не 4222: имя хоста становится `wss://host:443`, а `ws://host` использует 80. Задавайте порт явно.

**Использование `no_tls: true` в эксплуатации.** Это флаг разработки. Предупреждение `DO NOT USE IN
PRODUCTION!` — единственное сообщение сервера об этом, выводимое один раз при запуске.

**Сборка FIPS-140 старой версией Go.** Рукопожатие WebSocket вычисляет SHA-1 от `Sec-WebSocket-Key`. FIPS-сборка Go 1.25 или старше запрещает это, поэтому сервер отклоняет слушатель:

```
websocket: cannot be used in FIPS-140 mode when built with this Go
version, use Go 1.26 or later
```

По той же причине отклоняются удалённые адреса листовых узлов `ws://` и `wss://`. При сборке Go 1.26 или новее WebSocket нормально работает с FIPS: SHA-1 здесь лишь выводит ключ рукопожатия, а не защищает данные.

## Текущее состояние {#where-you-are}

У вас один сервер с двумя слушателями:

- Клиенты NATS на 4222, WebSocket — на 8080.
- `nats -s ws://127.0.0.1:8080 sub "orders.>"` получает публикации клиента `nats://`.
- Страница браузера показывает текущие `orders.>`.
- `no_tls: true` подходит локальной разработке, но не эксплуатации.

Сохраните сервер и `dashboard.html`: следующие страницы используют оба.
