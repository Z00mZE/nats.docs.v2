# Листовые узлы через WebSocket {#leaf-nodes-over-websocket}

Листовой узел может подключаться к центру через WebSocket вместо порта leafnode. Учётная запись, интерес к темам и поведение при потере связи прежние; меняется лишь транспорт. Базовая модель описана в [Топологии → Листовые узлы](/learn/topologies/leaf-nodes).

Причина обычно на стороне центра. Acme подключается к `east` через HTTPS ingress из раздела [TLS и прокси](/learn/websocket/tls-and-proxies). Порт leafnode через него не опубликован, слушатель WebSocket доступен — тот же, что у складской панели. Филиал с листовым узлом для касс использует этот вход.

## Сторона центра {#the-hub-side}

Центру нужны разрешённые соединения листовых узлов и слушатель WebSocket для их приёма.

```conf
# n1-east — hub
listen: 0.0.0.0:4222
server_name: n1-east

leafnodes {
  port: 7422
}

websocket {
  listen: 0.0.0.0:443
  tls {
    cert_file: "/etc/nats/certs/nats.acme.example.pem"
    key_file:  "/etc/nats/certs/nats.acme.example-key.pem"
  }
}
```

Здесь сертификат находится на слушателе. Вариант с `no_tls: true`, `advertise` и сертификатом на ingress работает для листовых узлов так же; конфигурация филиала ниже в обоих случаях одинакова.

Браузеры и листовые узлы используют один слушатель. Их отличает путь запроса: листовой узел запрашивает `/leafnode`, клиент — `/`. Сервер создаёт нужный вид соединения.

Вручную добавлять `/leafnode` не нужно: удалённый URL филиала остаётся `wss://host:443`, суффикс добавляет сервер. Это важно для прокси с маршрутизацией по пути. Если он обслуживает лишь `/nats`, запрос `/leafnode` не пройдёт. Укажите префикс в удалённом адресе `wss://host:443/nats`: получится `GET /nats/leafnode`, соответствующий правилу.

### Зачем оба блока, если филиал использует только 443 {#why-both-blocks-when-the-branch-only-uses-443}

Филиал подключается к `:443`, но `leafnodes` не избыточен. Блоки выполняют разные задачи:

- `leafnodes { port: 7422 }` включает приём листовых узлов **вообще**.
- `websocket {}` задаёт фактический вход филиала.

Без `leafnodes` либо с пустым `leafnodes {}` без порта WebSocket-соединение принимается и закрывается: центр не разрешает листовые узлы. Сам порт ими не используется, но блок необходим.

При этом 7422 — настоящий открытый слушатель, хотя WebSocket-узлам он не нужен. Ограничьте доступ к нему необходимыми участниками, как к другим портам. Правила межсетевого экрана описаны в разделе [Развёртывание → Защита](/learn/deployment/hardening).

## Сторона филиала {#the-branch-side}

Схема задаётся удалённым URL:

```conf
# branch till server
listen: 127.0.0.1:4222
server_name: branch-42

leafnodes {
  remotes [
    { urls: ["wss://nats.acme.example:443"] }
  ]
}
```

Это всё изменение: по сравнению с обычным leafnode-адресом схема — `wss://`, порт — 443.

Соединение достигает слушателя WebSocket центра, листовой узел регистрируется, интерес к темам распространяется в обе стороны, как через 7422.

## Что включает TLS {#what-turns-tls-on}

Достаточно одного из двух: схемы `wss://` или блока `tls {}` удалённого соединения. Одновременно оба не требуются.

Для центра с обязательным TLS на WebSocket:

| Удалённый адрес | TLS-рукопожатие | Результат |
|---|---|---|
| Только `ws://` | Нет | Отказ: центр ждёт TLS |
| `ws://` с `tls {}` | Да | Подключается |
| Только `wss://` | Да | Подключается с общедоверенным сертификатом центра |
| `wss://` с `tls {}` | Да | Подключается |

Адрес `wss://` выполняет рукопожатие и без `tls {}`. Если сертификату центра нет доверия, ошибка выглядит так:

```
[ERR] TLS leafnode handshake error: tls: failed to verify certificate:
      x509: certificate signed by unknown authority
```

Рукопожатие выполнялось, но проверка сертификата не прошла. Нужен `tls {}` с правильным CA, а не просто для включения TLS.

У `tls {}` две задачи: включить TLS, когда схема этого не сделала, и предоставить параметры проверки — отсутствующий в системном хранилище CA либо клиентский сертификат, если центр проверяет листовые узлы:

```conf
leafnodes {
  remotes [
    {
      urls: ["wss://nats.acme.example:443"]
      tls {
        ca_file: "/etc/nats/certs/acme-ca.pem"
      }
    }
  ]
}
```

С сертификатом общедоверенного CA блок `tls {}` филиалу вообще не нужен.

Следствие: **одна схема URL не определяет, зашифрована ли связь**. `ws://` рядом с `tls {}` использует TLS. Чтобы это было очевидно читающему конфигурацию, указывайте `wss://` явно.

## Одна схема в удалённом соединении {#one-scheme-per-remote}

Все URL одного удалённого соединения должны иметь однотипную схему. Смешение препятствует запуску:

```conf
remotes [
  { urls: ["wss://nats.acme.example:443", "nats://n2-east:7422"] }
]
```

```
nats-server: remote leaf node configuration cannot have a mix of
websocket and non-websocket urls: ["wss://nats.acme.example:443"
"nats://n2-east:7422"]
```

Это важно при добавлении второго адреса для отказоустойчивости. Все элементы списка должны использовать `wss://` и указывать на WebSocket-слушатели. Нельзя смешивать ingress и обычный leafnode-порт как взаимозаменяемые адреса.

Указывайте порт в каждом URL. Без него сервер добавляет `:7422` независимо от схемы: `wss://nats.acme.example` молча идёт на порт leafnode вместо 443 и не подключается, поскольку тот не использует WebSocket.

## Сжатие и маскирование {#compression-and-masking}

Две настройки относятся только к удалённым WebSocket-соединениям:

```conf
remotes [
  {
    urls: ["wss://nats.acme.example:443"]
    ws_compression: true
    ws_no_masking: true
  }
]
```

`ws_compression` запрашивает согласование сжатия. Как у клиентов, CPU на обеих сторонах обменивается на сетевые байты. Листовое соединение передаёт подписки филиала; пользу нужно измерять на его трафике и канале.

`ws_no_masking` просит принимать немаскированные кадры. Стандарт WebSocket требует маскирования от клиента для защиты промежуточных кэшей от воздействия браузера; для связи серверов этот риск неприменим. Настройка убирает маскирование каждого кадра. Обе настройки — запросы: решение принимает центр, при отказе связь всё равно работает.

Длинные псевдонимы `websocket_compression` и `websocket_no_masking` означают то же.

## Ограничение учётных данных {#restricting-the-credential}

Данные филиала не должны работать для обычного клиента. Тип соединения листового узла WebSocket — `LEAFNODE_WS`, а не `LEAFNODE`:

```conf
authorization {
  users [
    { user: branch-42, password: s3cr3t, allowed_connection_types: ["LEAFNODE_WS"] }
  ]
}
```

`LEAFNODE` отклоняет филиал: допустимый тип включает используемый транспорт.

## Подводные камни {#pitfalls}

**Определение шифрования только по схеме.** `ws://` с `tls {}` зашифрован, как и один `wss://`. Проверьте схему и блок вместе, прежде чем считать связь открытой.

**Смешение схем в `urls`.** Сервер не запустится. Либо все адреса удалённого соединения используют `wss://`, либо ни один.

**Удалённый адрес указывает на порт leafnode.** Филиалу нужен слушатель *WebSocket*. Порт 7422 напрямую использует протокол листовых узлов и не завершает WebSocket-рукопожатие.

**Разрешение `LEAFNODE` узлу WebSocket.** Тип должен соответствовать транспорту: нужен `LEAFNODE_WS`.

**Прокси не передаёт `/leafnode`.** Сервер добавляет этот суффикс к пути URL, поэтому правило только `/nats` не подходит исходному запросу. Обслуживайте `/` либо добавьте префикс в URL, получив `/nats/leafnode`.

**На центре отсутствует слушатель WebSocket.** Транспорт должен поддерживаться с обеих сторон. Одного leafnode-порта для `wss://` недостаточно.

## Текущее состояние {#where-you-are}

Филиал подключён к общей системе через тот же вход, что и панель:

- Центр предоставляет WebSocket со сертификатом для браузеров и листовых узлов.
- Филиал подключается к `wss://nats.acme.example:443` и регистрируется обычным листовым узлом.
- Схема включает TLS; `tls {}` добавляет CA лишь для сертификата без общего доверия.
- Учётные данные ограничены `LEAFNODE_WS`.
