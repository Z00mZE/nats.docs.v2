# Масштабирование и управление участниками {#scaling-and-peer-management}

`ORDERS` работает с `R=3` на `n1-east`, `n2-east`, `n3-east` согласно [размещению](/learn/clustering/placement). Состав не фиксирован навсегда: можно увеличить число копий или перенести реплику с выводимого сервера без остановки потока и потери согласованности.

Здесь меняется состав работающей группы RAFT. **Участник** — роль сервера в группе `ORDERS`, как определено в [RAFT и лидерах](/learn/clustering/raft-and-leaders). Управление состоит из **расширения группы** с синхронизацией нового участника и **переноса реплики** с сервера.

<div class="nats-flow" data-scenario="peerScalingAnimated" data-width="600" data-height="350"></div>

Анимация показывает обе части: четвёртый сервер получает недостающие записи и догоняет группу; затем реплика уходит с сервера, который снимает свои подписки RAFT, пока остальные продолжают работу.

## Расширение группы: синхронизация нового участника {#growing-the-group-a-new-peer-catches-up}

Увеличьте число реплик потока. Четвёртый сервер уже должен входить в `east`: запустите `n4-east` с конфигурацией [первой страницы](/learn/clustering/forming-a-cluster), дождитесь присоединения, затем увеличьте `ORDERS` с трёх до четырёх реплик:

```bash
nats --server nats://127.0.0.1:4222 stream edit ORDERS --replicas=4
```

Имя нового сервера не задаётся. Лидер метаданных выбирает узел, подходящий под [размещение](/learn/clustering/placement), записывает состав в журнал назначений, и группа `ORDERS` принимает `n4-east`.

Новый участник пока не содержит историю потока. Сначала выполняется **догоняющая синхронизация**: лидер передаёт недостающую часть журнала, участник применяет записи, а отставание стремится к нулю. Здесь оно измеряет число недостающих записей журнала лидера.

Добавление сразу меняет кворум: `R=4` требует трёх держателей записи вместо двух. Пока журнал пуст, новый участник не может победить на выборах: он остаётся наблюдателем до первых записей лидера. Практическое правило — не считать `n4-east` полноценной копией данных до отметки `current` в `stream info`.

Наблюдайте синхронизацию в блоке `Cluster` команды `nats stream info`:

```bash
nats --server nats://127.0.0.1:4222 stream info ORDERS
```

В `Replicas` появилась четвёртая запись с уменьшающимся отставанием:

```
Cluster Information:

                Name: east
              Leader: n1-east
             Replica: n2-east, current, seen 0.12s ago
             Replica: n3-east, current, seen 0.20s ago
             Replica: n4-east, outdated, seen 0.18s ago, 14,231 operations behind
```

`outdated` и число недостающих операций означают продолжающуюся синхронизацию. После `current` без отставания `n4-east` содержит полный поток и работает как обычная реплика.

## Перенос реплики с сервера {#moving-a-replica-off-a-server}

Для освобождения сервера выполните **эвакуацию** участника. Она не уменьшает поток: реплика переносится на другой подходящий сервер при сохранении количества. Укажите поток и освобождаемый узел:

```bash
nats --server nats://127.0.0.1:4222 stream cluster evacuate ORDERS n4-east
```

Лидер метаданных выбирает замену и записывает новый состав, но `n4-east` пока остаётся в группе. Замена присоединяется и синхронизируется; только после её готовности фиксируется изменение, исключающее `n4-east`. Если уходящий узел был лидером, до ухода выбирается новый.

Если размещение не допускает замену, запрос возвращает `peer remap failed` и ничего не меняет. Это защищает заданное число реплик. Исправьте условия или добавьте подходящий сервер, затем повторите.

Потребители перемещаются вместе с потоком. Отдельного потребителя тоже можно перенести:

```bash
nats --server nats://127.0.0.1:4222 consumer cluster evacuate ORDERS NEW n4-east
```

Чтобы изменить *количество*, например `R=3` на `R=1`, используйте `nats stream edit ORDERS --replicas=1`. Эвакуация меняет расположение, `--replicas` — число копий.

Сразу после команды группа может ещё перемещаться. Оба участника видны одновременно, замена отстаёт, а присоединяющийся или уходящий узел отмечен `(pending)`.

<div class="nats-example" data-type="learn-clustering-scaling-and-peers-evacuate" data-languages="cli"></div>

Перенос завершён, когда `n4-east` исчез из `Replicas`, а `stream info` больше не показывает раздел миграции. Не используйте нулевое отставание как единственный критерий: при постоянных записях ведомые могут немного отставать, поскольку фиксация требует кворума, а не всех копий. Если перенос завис, строка состояния миграции объяснит ожидание; её разбирает [следующая страница](/learn/clustering/desired-state).

Удаление сервера из **группы метаданных** — другая команда: `nats server cluster peer-remove`. Она разрешает лишь одно изменение одновременно; повторное возвращает `cluster member change is in progress`. Дождитесь завершения. Эта операция предназначена для навсегда потерянного сервера, а для работающего применяется эвакуация.

Перед peer-remove обязательно остановите сервер. Работающий узел в ответ отключает у себя JetStream — это прервёт обслуживание вместо удаления уже остановленного участника.

Все операции управления участниками и назначениями описаны в [справочнике](/reference/jetstream/api/meta). Здесь нужны расширение, перенос и проверка.

## Типичные ошибки {#pitfalls}

Две распространённые ошибки связаны с синхронизацией нового участника и переносом реплики.

**Расширение временно уменьшает запас устойчивости.** Переход с трёх реплик на четыре повышает кворум с двух до трёх. Новый участник ещё не имеет истории и до синхронизации не может дать необходимое подтверждение, поэтому требуются все три исходных узла. Потеря одного приостанавливает запись до готовности нового. Временно четыре реплики терпят меньше отказов, чем прежние три. Окно закрывается при `current` нового участника.

**`peer remap failed` означает безопасный отказ без изменений.** При отсутствии подходящего сервера эвакуация потока или потребителя отклоняется вместо потери реплики. Исправляйте размещение или добавляйте ресурсы, не обходите отказ через `--force`. Иначе ведёт себя лишь общесерверный `nats server cluster evacuate`: он освобождает узел по возможности и может оставить ресурс с недостаточным числом реплик. Различие разобрано на [следующей странице](/learn/clustering/desired-state).

Эвакуация не меняет число копий. Для `R=3` → `R=1` прочитайте текущее значение и примените `nats stream edit --replicas`.

## Что уже готово {#where-you-are}

Теперь вы умеете менять работающую группу RAFT без остановки потока:

- Увеличивать `--replicas` и ждать синхронизации до `current`.
- Переносить реплику через `nats stream cluster evacuate`, сохраняя количество и проверяя лидера.
- Понимать `peer remap failed` как защиту числа реплик без выполненного перемещения.

`ORDERS` снова находится на `n1-east`, `n2-east`, `n3-east`, но теперь вы умеете осознанно менять состав.
