# Желаемое состояние и эвакуация {#desired-state-and-evacuation}

[Предыдущая страница](/learn/clustering/scaling-and-peers) меняла состав `ORDERS` по одному участнику. Начиная с 2.15 масштабирование, перенос, изменение размещения или хранения записываются как **желаемое состояние**: итоговый набор участников. Серверы самостоятельно приводят систему к нему, а вы можете видеть продвижение.

Здесь мы прочитаем это состояние, перенесём все ресурсы сервера одной командой и отменим ошибочно начатое изменение.

## Что записывает сервер {#what-the-server-records}

До 2.15 цель изменения явно не сохранялась. Лидер метаданных выбирал и добавлял участников; единственный признак процесса — расхождение их числа с числом реплик. Лидер потока ждал синхронизации и предлагал удалить старых. Намерение выводилось из количества, а не хранилось явно: нельзя было спросить о цели или восстановить прежнюю по сохранённой записи.

Теперь в назначение записываются итоговый кластер, участники и прежняя конфигурация. Все серверы сходятся к этой цели. Благодаря записи можно наблюдать процесс и отменять его.

В `nats stream info` появляется отдельный раздел под `Cluster Information`. Запустите перенос `ORDERS` из `east` в `west` и посмотрите:

```bash
nats --server nats://127.0.0.1:4222 stream info ORDERS
```

```
Cluster Information:

                Name: east
              Leader: n1-east
             Replica: n2-east, current, seen 0.10s ago
             Replica: n3-east, current, seen 0.14s ago
             Replica: n1-west, outdated, seen 0.11s ago, (pending), 9,102 operations behind

   Cluster Migration Status:

              Status: moving stream to cluster west
             Created: 2026-09-18 09:41:22 (1m18s)

             Cluster: east -> west
       Desired Peers: n1-west, n2-west, n3-west
```

**Desired peers** — целевой набор участников. Строки `Replica` выше показывают текущий. Во время изменения списки различаются, после завершения совпадают.

**`(pending)`** означает, что узел назначен, но ещё не полноценный участник RAFT: он присоединяется или уходит. Он не учитывается в кворуме, поэтому перенос сохраняет фиксацию на прежних участниках.

**Origin** — конфигурация до начала операции, которую возвращает откат. CLI показывает её строками `from -> to`, например `Cluster: east -> west`. Масштабирование даст `Replicas: 3 -> 5`, изменение политики — `Retention Policy: Limits -> Interest`.

Если раздела нет, активного изменения нет.

## Перенесите все ресурсы с сервера {#move-everything-off-a-server}

Раньше для вывода `n4-east` требовалось найти каждую реплику потока и потребителя и переносить отдельно. Теперь достаточно имени сервера:

```bash
nats --server nats://127.0.0.1:4222 server cluster evacuate n4-east
```

Лидер метаданных сохраняет желаемое состояние для всех ресурсов `n4-east`, оставляя требуемое число реплик, и подбирает замены по условиям размещения. Без имени CLI перечислит участников и предложит выбрать.

Замена выполняется **по возможности**. Цель — освободить сервер. Если другого места нет из-за условий или размера кластера, ресурс всё равно уходит с `n4-east` и остаётся **с недостаточным числом реплик** до появления подходящего узла. Поток `R=3` может временно работать на двух участниках. Сервер пишет `could not replace peer for stream`, а `nats stream
info` показывает недостаток. Проверяйте важные потоки после операции. Освобождаемый сервер исключается из их размещения, чтобы реплика не вернулась до его удаления.

Как и остальные `nats server cluster`, команда требует системной учётной записи.

Для переноса не всего сервера есть более узкие команды. Они предпочитают отказ уменьшению числа реплик. Один поток со всеми потребителями:

```bash
nats --server nats://127.0.0.1:4222 stream cluster evacuate ORDERS n4-east
```

Один потребитель:

```bash
nats --server nats://127.0.0.1:4222 consumer cluster evacuate ORDERS NEW n4-east
```

Обе возвращают `peer remap failed` без изменений, если нет подходящей замены. Потеря реплики отдельного потока хуже невыполненной команды. Только общесерверная эвакуация продолжает работу, поскольку её цель — полностью освободить узел.

Все три по возможности сохраняют число реплик и автоматически выбирают замену. В отличие от них `nats stream edit --replicas` меняет количество копий. Эвакуация меняет только место.

*Удаление* участника — другая операция: он исключается без предварительного переноса на замену. Это нужно для навсегда потерянного сервера в [аварийном восстановлении](/learn/backup-recovery/disaster-recovery). Для работающего узла используйте эвакуацию.

Перед удалением сервер должен быть остановлен. Peer-remove — очистка сведений об уже ушедшем узле. Работающий сервер в ответ отключает JetStream у себя.

## Откат изменения конфигурации {#roll-a-reconfiguration-back}

Если во время операции нужно отменить перенос, выполните:

```bash
nats --server nats://127.0.0.1:4222 stream cluster cancel-move ORDERS
```

Поток возвращается к конфигурации и участникам из `origin`: прежним репликам, размещению и политике хранения.

Несмотря на имя, команда отменяет не только перенос: так же отменяются незавершённое масштабирование `R=3` → `R=5` и изменение политики хранения. Понимайте её как «отменить изменение конфигурации».

Перед действием выполняются две проверки:

- Если поток не кластерный, возвращается `stream is not clustered`.
- Если изменения нет — раздел `Cluster Migration Status` отсутствует, — возвращается `stream is not busy moving`.

Затем запрашивается подтверждение. `--force` пропускает и проверки, и запрос; поэтому не начинайте с него.

## Типичные ошибки {#pitfalls}

**Не отменяйте почти завершённый перенос.** Откат сам является изменением состава с обратной синхронизацией прежних участников. Если осталось несколько секунд, дешевле завершить и затем перенести обратно. Сначала сравните `Desired Peers` и `Replica`.

**`--force` скрывает отсутствие операции для отмены.** Без него `stream is not busy moving` сообщает, что перенос уже завершён. С ним команда отправится потоку без желаемого состояния. Сначала запускайте без принуждения; используйте его лишь при известной активной операции, когда мешает только запрос подтверждения.

**Общесерверная эвакуация может оставить недостаток реплик.** Отдельные команды отказывают без замены; `nats server
cluster evacuate` освобождает узел всё равно. При отсутствии запаса или узких условиях потоки теряют реплику. Проверяйте `nats stream info` после вывода и планируйте ресурсы так, чтобы один узел мог уйти.

**Смешанные версии 2.14 и 2.15 не завершают изменение.** Сервер 2.14 сохраняет желаемое состояние, но не доводит его до конца: масштабирование или перенос зависнут до обновления всех узлов. Код совместимости есть начиная с 2.14.7; поэтому [инструкция обновления](/release-notes/upgrade-to-2.15) требует как минимум эту версию.

## Что уже готово {#where-you-are}

Теперь вы можете наблюдать и направлять изменение состава:

- Читать `Cluster Migration Status`, различать желаемых и текущих участников и видеть `(pending)`, не учитываемых в кворуме.
- Переносить все ресурсы с `n4-east` через `nats server cluster evacuate` либо использовать отдельные команды потоков и потребителей.
- Различать операции, допускающие недостаток реплик, и отказы `peer remap failed`.
- Отменять перенос, масштабирование и смену хранения через `nats stream cluster cancel-move`.
