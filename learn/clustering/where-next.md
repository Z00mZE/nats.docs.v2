# Куда двигаться дальше {#where-to-go-next}

В начале ничего не было запущено. Теперь три сервера `n1-east`, `n2-east`, `n3-east` обнаружили друг друга через один начальный маршрут, выбрали лидеров групп RAFT и хранят `ORDERS` с `R=3`. Запись `order-svc` приходит лидеру, фиксируется кворумом и переживает отказ одного сервера.

Эта страница собирает механизм целиком и указывает главы и справочник для дальнейшего изучения.

## Пять основных идей {#the-five-core-ideas}

Все страницы опирались на пять идей.

**Маршруты** — соединения серверов, формирующие кластер. Вы задаёте начальный явный маршрут, а gossip распространяет известные адреса через INFO и достраивает полносвязную сеть.

**Группы RAFT** обеспечивают согласование: общая группа метаданных и отдельная у каждого потока. Выборы назначают единственного лидера, принимающего записи; ведомые реплицируют их.

**Кворум** — большинство: два из трёх для `R=3`. Лидер фиксирует запись, когда она есть у кворума. Так группа продвигается при недоступном меньшинстве и синхронизирует его после возвращения.

**Размещение** определяет серверы реплик. Ограничьте поток кластером и метками, а лидер метаданных выберет подходящие узлы.

**Управление участниками** меняет состав. После увеличения числа реплик ждите синхронизации нового узла; переносите реплики по очереди, сохраняя большинство.

Маршруты, RAFT, кворум, размещение и участники — всё остальное, включая сроки, выборы, append entry, применение и миграцию, уточняет эти идеи.

## Где искать подробности {#where-the-details-live-now}

Глава объясняет понятия и не привязана к версии. Точные таймеры выборов, формат WAL, поля `cluster {}` и `StreamConfig` находятся в версионируемом **справочнике**. Там ищите типы настроек и сетевой формат маршрутов.

Начните с [корня справочника](/reference/). Все ссылки главы на полные описания ведут туда. Чаще всего нужны:

- [Конфигурация `cluster {}`](/reference/config/cluster) и [протокол маршрутов](/reference/protocols/route) — поля формирования кластера.
- [API потоков](/reference/jetstream/api/stream) и [метки серверов](/reference/config/server_tags) — реплики и размещение.
- [`/jsz`](/reference/system/monitor/jsz) и [`/raftz`](/reference/system/monitor/raftz) — конечные точки мониторинга для показателей CLI.

## Связанные главы {#sibling-deep-dives}

Эта глава объясняет механизм под двумя другими: зависимости взаимны.

[Топологии](/learn/topologies) выбирают форму: один сервер, кластер, суперкластер или листовые узлы. Оттуда взят `east`. Там решается, *что* строить; здесь — *как* оно согласует и реплицирует данные.

[JetStream](/learn/jetstream) создал реплицируемый `ORDERS`. Его [Отказ узла](/learn/jetstream/surviving-node-loss) кратко вводит `R=3`, а здесь подробно разобраны выборы и фиксация кворумом. Для копий *между* кластерами и аварийного восстановления читайте [зеркала и источники](/learn/jetstream/mirrors-and-sources).

[Развёртывание](/learn/deployment) объясняет эксплуатацию на реальной инфраструктуре: Kubernetes, последовательные обновления и расчёт серверов.

[Резервное копирование и восстановление](/learn/backup-recovery) защищает данные снимками перед рискованной сменой состава и восстанавливает после неудачной миграции.

## Что уже готово {#where-you-are}

Глава завершена; новых изменений сценария нет. `east`, избранные лидеры и `ORDERS` с `R=3` продолжают работать. Можно экспериментировать с отказом сервера, пятым участником и размещением либо удалить `ORDERS` через `nats stream rm ORDERS` и остановить серверы после работы.

Основная модель освоена: маршруты строят сеть, RAFT согласует, кворум фиксирует записи, размещение выбирает узлы, управление меняет состав без потери согласованности. Это минимум для эксплуатации кластера NATS.

## Контрольный список перед эксплуатацией {#production-checklist}

Здесь собраны действия из типичных ошибок для последней проверки перед реальными заказами. Каждая группа ссылается на объяснение причин.

### Формирование кластера — см. [Типичные ошибки](/learn/clustering/forming-a-cluster#pitfalls) {#forming-a-cluster--see-pitfalls}

- [ ] Задайте одинаковый `cluster.name` всем серверам: несовпадение разделяет систему на кластеры.
- [ ] Направляйте `routes` на маршрутный 6222, а не клиентский 4222.
- [ ] Укажите два-три начальных адреса, чтобы запуск переживал недоступность одного; gossip достаточно одного доступного.

### RAFT и лидеры — см. [Типичные ошибки](/learn/clustering/raft-and-leaders#pitfalls) {#raft-and-leaders--see-pitfalls}

- [ ] Считайте короткую паузу «нет лидера» нормальной: таймер выборов составляет 4–9 секунд, клиент должен повторить запрос.
- [ ] Используйте `nats stream cluster step-down` для освобождения роли; победителя выбирает кворум. Читайте `nats stream info` после команды.
- [ ] Различайте группы лидера метаданных и лидера потока: проверяйте `nats server report jetstream` и `nats stream info ORDERS` соответственно.

### Репликация и R=3 — см. [Типичные ошибки](/learn/clustering/replication-and-r3#pitfalls) {#replication-and-r3--see-pitfalls}

- [ ] Для рабочих заказов используйте `R≥3`: единственная копия `R=1` теряется вместе с диском.
- [ ] Для чтения после записи обращайтесь к лидеру: Direct Get ведомого может вернуть ещё не обновлённые данные.
- [ ] Понимайте `PubAck` как наличие кворума, а не всех копий. Перед плановой остановкой проверяйте `current` каждой реплики.

### Размещение — см. [Типичные ошибки](/learn/clustering/placement#pitfalls) {#placement--see-pitfalls}

- [ ] Сначала прочитайте фактические метки серверов: пересечение с отсутствующей меткой даёт `no suitable peers for placement`.
- [ ] Проверяйте написание: `ssd` и `SSD` эквивалентны, `sdd` — другая метка.
- [ ] Размещение не назначает лидера. Используйте `nats stream cluster step-down --preferred` на NATS Server 2.11+, понимая, что выборы могут отклонить пожелание.

### Масштабирование и управление участниками — см. [Типичные ошибки](/learn/clustering/scaling-and-peers#pitfalls) {#scaling-and-peer-management--see-pitfalls}

- [ ] Дождитесь `current` нового участника до опоры на его данные; не останавливайте другой сервер во время синхронизации.
- [ ] `peer remap failed` от `nats stream cluster evacuate` означает отсутствие переноса. Исправьте размещение или добавьте место и повторите.
- [ ] Меняйте число копий через `nats stream edit --replicas`: эвакуация меняет только расположение.

### Желаемое состояние и эвакуация — см. [Типичные ошибки](/learn/clustering/desired-state#pitfalls) {#desired-state-and-evacuation--see-pitfalls}

- [ ] Сравнивайте `Desired Peers` и `Replica` перед отменой: откат почти завершённого переноса требует лишней синхронизации.
- [ ] Сначала запускайте `nats stream cluster cancel-move` без `--force`, чтобы узнать об уже завершённой операции через `stream is not busy moving`.
- [ ] Не начинайте переносы и масштабирование до обновления всех узлов до 2.15. Обновляйтесь с 2.14.7 или новее: старые узлы сохраняют цель, но не завершают её.
- [ ] После `nats server cluster evacuate` проверяйте важные потоки: при отсутствии замены они могут остаться с недостатком реплик.
