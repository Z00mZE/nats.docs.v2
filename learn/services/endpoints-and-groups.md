# Конечные точки и группы {#endpoints-and-groups}

На предыдущей странице вы запустили сервис `OrderInventory` с одной конечной точкой `check`, отвечающей на `orders.inventory.check`. Это минимальная полезная структура: один сервис, один обработчик, один субъект.

Реальные сервисы редко остаются такими маленькими. Обычно сервис отвечает более чем на один вид запросов, и тогда субъекты хочется упорядочить. Эта страница добавляет две необходимые возможности: сервис может содержать несколько конечных точек, а группа задаёт набору конечных точек общий префикс субъектов.

К концу страницы рядом с `OrderInventory` появится второй сервис `ShippingQuote`, и вы научитесь размещать несколько конечных точек под одним префиксом.

## Сервис может содержать несколько конечных точек {#a-service-can-hold-multiple-endpoints}

**Конечная точка** — именованный обработчик на субъекте. С одной вы познакомились на предыдущей странице; сервис может содержать несколько таких точек. Каждый вызов `AddEndpoint(name, handler)` регистрирует ещё один именованный обработчик, причём **субъект конечной точки по умолчанию равен её имени**.

Добавьте второй сервис так же, как первый. `ShippingQuote` превращает поставщиков ответов Core NATS на `shipping.quote` в именованный сервис. У него одна конечная точка `quote`; чтобы она отвечала на `shipping.quote`, а не просто на `quote`, задайте субъект явно:

Теперь два сервиса работают с одним `nats-server`. `OrderInventory` отвечает на `orders.inventory.check`, а `ShippingQuote` — на `shipping.quote`. Они независимы: у каждого своё имя, версия и обнаружение. Фреймворк автоматически назначил каждому уникальный идентификатор сервиса.

Если субъект должен совпадать с именем конечной точки, его можно не задавать. Конечная точка `quote` без явного субъекта отвечает на `quote`. Явное значение нужно, когда сетевой субъект отличается от имени конечной точки; это обычная ситуация для структурированных субъектов вроде `orders.inventory.check`.

Контракт обработчика не изменился: запрос читается через `req.Data()`, ответ отправляется через `req.Respond()`. Добавление конечных точек не меняет обработку отдельного запроса; оно лишь добавляет именованные обработчики к тому же работающему сервису.

## Группа — префикс субъекта {#a-group-is-a-subject-prefix}

Когда у сервиса больше одной конечной точки, в субъектах появляются повторы. Две конечные точки проверки запасов естественно назвать `orders.inventory.check` и `orders.inventory.reserve`: основа `orders.inventory` повторяется. **Группа** позволяет задать её один раз.

`AddGroup("orders.inventory")` возвращает группу, и любая добавленная в неё конечная точка отвечает на `{group}.{endpoint}`. Точка `check` в группе `orders.inventory` отвечает на `orders.inventory.check`, а `reserve` — на `orders.inventory.reserve`. Вы задаёте префикс один раз, а фреймворк соединяет его с именем каждой точки.

<div class="nats-example" data-type="learn-services-endpoints-and-groups-addGroup" data-languages="cli,js,go,python,java,rust,csharp,c"></div>

Вызывающая сторона всегда отправляет запрос на `{group}.{endpoint}`. Отдельного слоя маршрутизации нет: группа лишь помогает составить субъект. Клиенту, знающему субъект, не нужно знать, добавлена конечная точка напрямую или через группу. Сетевой обмен одинаков в обоих случаях.

Группы могут быть вложенными. Группа внутри другой группы объединяет оба префикса, и субъект становится `{outer}.{inner}.{endpoint}`. Для сервиса такого размера редко нужен более чем один уровень, но префиксы складываются ожидаемым образом.

## Группа может задавать группу очереди {#a-group-can-set-the-queue-group}

Каждая конечная точка входит в **группу очереди** — группу балансировки нагрузки, благодаря которой сервер доставляет каждый запрос ровно одному участнику. Имя по умолчанию — `"q"`; вы уже использовали его без явной настройки: все экземпляры `OrderInventory` входят в `"q"`, поэтому запрос получает один из них. Сам механизм объясняется в [Core NATS](/learn/core-nats/queue-groups); здесь это уже действующее значение по умолчанию для конечной точки сервиса.

Группа очереди задаётся на трёх уровнях, и каждый переопределяет предыдущий. Сервис устанавливает значение по умолчанию. Группа может переопределить его для всех своих конечных точек. Отдельная конечная точка может переопределить его ещё раз. Если значение нигде не задано, используется `"q"`.

Группа очереди конечной точки переопределяется одним параметром. Здесь `check` входит в пользовательскую группу вместо стандартной `"q"`:

Анимация выделяет правило маршрутизации. Один сервис содержит две конечные точки: `check` на `orders.inventory.check` и сгруппированную `quote` на `shipping.quote`. Субъект запроса выбирает обработчик: запрос к `orders.inventory.check` запускает `check`, запрос к `shipping.quote` — `quote`; работает лишь точка с совпадающим субъектом. ## Подводные камни {#pitfalls}

У конечных точек и групп есть две распространённые ловушки: одна связана с группой очереди, другая — с необратимыми изменениями.

**Отключение группы очереди делает конечную точку широковещательной.** Переопределение группы меняет, *кто с кем* балансирует нагрузку. Полное отключение меняет поведение сильнее: конечная точка становится обычной подпиской, поэтому **каждый экземпляр** получает **каждый** запрос. Для конечной точки запросов и ответов это означает по одному ответу от каждого экземпляра, из которых лишние создают шум. Не отключайте группу, чтобы «запрос точно обработали»: именно это уже обеспечивает стандартная `"q"`, с одним обработчиком вместо N. Отключайте её, только когда действительно нужно действие всех экземпляров, что редко требуется отвечающему сервису.

Этим управляет один параметр. Переопределяйте группу очереди, если часть конечных точек должна балансироваться отдельно; не отключайте её на отвечающей конечной точке. Отправьте запрос и проверьте, в какую группу вошла точка: стандартную `"q"`, переопределённую или никакую:

**После добавления конечные точки неизменяемы.** Операции удаления нет. Нельзя отсоединить точку, переименовать её или изменить субъект работающего сервиса. То же относится к метаданным сервиса и конечной точки: они фиксируются при создании. Для изменения структуры нужно остановить сервис и запустить новый с другой конфигурацией. Выбирайте имена и субъекты до запуска сервиса осознанно и сразу, как имя потока в JetStream.

## Текущее состояние {#where-you-are}

Теперь у вас есть:

- Два сервиса с одним `nats-server`: `OrderInventory` отвечает на `orders.inventory.check`, а `ShippingQuote` — на `shipping.quote`.
- Возможность добавлять конечные точки к каждому из них с субъектами, по умолчанию равными имени точки.
- Группа для общего префикса связанных конечных точек и три уровня задания группы очереди.

Оба сервиса по-прежнему делают то же, что их обработчики Core NATS. Добавилась структура: имена, субъекты и балансировка нагрузки фреймворка по умолчанию.
