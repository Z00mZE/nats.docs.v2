# Первый бакет {#your-first-bucket}

Пора создать бакет `INVENTORY`. Сервис inventory хранит остаток каждого артикула, а бакет — место хранения этих значений. Здесь мы одной командой создадим бакет, запишем количество, прочитаем его и посмотрим состояние бакета.

Предыдущая глава познакомила с JetStream. Бакет работает поверх него: **бакет** — поток JetStream, который API ключей и значений создаёт и настраивает за вас. Вручную описывать поток не нужно. Вы запрашиваете бакет с понятным именем `INVENTORY`, а сервер хранит за ним поток `KV_INVENTORY`. Он рассматривается на странице [Внутреннее устройство](/learn/key-value/under-the-hood); пока достаточно знать о его существовании.

## Создание бакета {#create-the-bucket}

Единственное требование — работающий `nats-server` с включённым JetStream. API ключей и значений входит в JetStream, поэтому без `-js` следующей команде не с чем взаимодействовать:

```bash
nats-server -js
```

В команде важны две части. Первая — **имя бакета** `INVENTORY`. Имена чувствительны к регистру и встречаются в каждой команде и сообщении об ошибке этой главы. Имя напрямую отображается на базовый поток: `INVENTORY` становится `KV_INVENTORY`.

Вторая — `--history 1`. **История** задаёт число сохраняемых значений каждого ключа. Единица означает хранение только текущего значения без предыдущих. Это значение по умолчанию, и сервису inventory его пока достаточно. Глубину можно увеличить до 64, но не выше. В разделе [История и ревизии](./history-and-revisions.md) мы увеличим её, чтобы сохранять прошлое ключа; пока хватит единицы.

Другую конфигурацию вы не задавали. За бакетом стоит длинный список настроек потока с разумными значениями по умолчанию. Полный перечень приведён в разделе [Справочник → Создание потока](/reference/jetstream/api/stream/create), поскольку бакет создаётся как поток. Здесь используем только `History`.

## Запись значения и получение записи {#put-a-value-get-an-entry}

Бакет пуст. Поместите в него первый остаток товара. **Ключ** — артикул, а **значение** — количество, сохранённое в виде байтов:

<div class="nats-example" data-type="learn-key-value-your-first-bucket-putValue" data-languages="cli,js,go,python,java,rust,csharp,c"></div>

Это **put** — безусловная запись. Она сохраняет значение независимо от существования ключа. Каждая запись также получает **ревизию**: число из единого счётчика всего бакета, а не отдельного ключа. Поскольку `INVENTORY` пуст, первая запись получает ревизию 1. При наличии других ключей та же операция взяла бы следующий номер общей последовательности. API put возвращает ревизию клиентскому коду; CLI выводит только сохранённое значение. Ревизии отслеживают изменения во времени; на них опирается раздел [История и ревизии](./history-and-revisions.md).

Теперь прочитайте значение:

<div class="nats-example" data-type="learn-key-value-your-first-bucket-getValue" data-languages="cli,js,go,python,java,rust,csharp,c"></div>

**Get** возвращает **запись**, а не голое значение: значение вместе с ревизией и временем записи. Флаг CLI `--raw` оставляет только байты значения (`42`), что часто нужно программе, однако сервер фактически отправляет полный объект.

Это намеренная структура: сервису inventory редко нужно только количество. Ему нужны количество *и* ревизия для безопасного уменьшения, описанного в разделе [История и ревизии](/learn/key-value/history-and-revisions). Запись содержит оба значения за одно чтение: отдельный вызов для определения прочитанной ревизии не нужен.

Временная метка также важна. Она фиксирует момент записи значения, а не чтения: сервис отличает остаток, обновлённый несколько секунд назад, от неизменного в течение недели. Один get даёт все три сведения: значение, ревизию и время записи.

## Подводные камни {#pitfalls}

При работе с первым бакетом распространены две ошибки. Зная о них, обе легко избежать.

**Get возвращает запись, а отсутствие ключа отличается от пустого значения.** Непосредственное чтение байтов работает только при существующем ключе. Никогда не записанный ключ не возвращает пустую запись: CLI и некоторые клиенты (Go, Python, C#) сообщают об ошибке отсутствия ключа, другие (JavaScript, Rust, Java) возвращают null или None. В любом случае отсутствие обозначается отдельно от значения, которое оказалось пустым: пустое значение существует, отсутствующий ключ — нет. Не считайте отсутствие ключа нулевым остатком. Пример get выше заканчивается именно таким случаем: запрашивается артикул, который никогда не поступал на склад; get сообщает об отсутствии, и программа решает, что это значит, вместо случайного чтения устаревшего или нулевого количества. Сначала проверяйте наличие записи, затем читайте значение.

**Имена бакетов и ключей проверяются.** Имя бакета может содержать только буквы, цифры, дефис и подчёркивание и не может быть пустым. Ключ допускает больше символов: буквы, цифры, `-`, `/`, `_`, `=` и `.`, но ничего сверх этого. Точка не может быть первой или последней, а две точки подряд запрещены: `a..b` отклоняется, хотя `a.b` допустимо. Идентификатор заказа `ord:8w2k` содержит двоеточие и не подходит для ключа. Клиентская библиотека проверяет имя и отклоняет запись до отправки, не позволяя сохранить некорректный ключ. Выбирайте допустимые имена и заменяйте двоеточие подчёркиванием или дефисом:
