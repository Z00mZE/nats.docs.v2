# Отладка доставки {#debugging-delivery}

Вы публикуете `orders.created`, но упаковщик не упаковывает заказ. Публикация вернулась без ошибки, сообщение покинуло клиента, однако ничего не пришло. В Core NATS у этого три причины:

- В момент публикации никто не был подписан: серверу некому доставлять, и сообщение отброшено.
- Подписка есть, но на другую тему. Опечатка или лишний сегмент направляет сообщение мимо подписчиков.
- Подписчик работает, но соединение разорвано, и его интерес уже удалён из графа сервера.

Обычная публикация не даёт обратной связи для различения случаев. Это [отправка без ожидания](/learn/core-nats/publish-subscribe): издатель не видит число получателей и само наличие доставки. Запрос хотя бы сообщает об отсутствии подписчиков через [no responders](/learn/core-nats/request-reply#no-responders), а односторонняя публикация молчит. Здесь описаны три инструмента, показывающих происходящее для разных причин.

## Просмотр сообщений через перехват трафика {#see-every-message-with-a-wire-tap}

Быстрее всего проверить отправку и точную тему непосредственным наблюдением трафика. Подпишитесь на многосегментный символ `>`: сервер пришлёт копию каждой публикации вашей учётной записи. Такая подписка `>` для наблюдения, а не бизнес-логики, называется **перехватом трафика (wire tap)**.

<div class="nats-example" data-type="learn-core-nats-debugging-delivery-wire-tap" data-languages="cli"></div>

Каждая строка показывает точную тему публикации:

```text
12:30:25 Subscribing on >
[#1] Received on "orders.us.created"
{"order_id":"ord_8w2k","customer":"acme-co","total_cents":4200,"ts":"2026-05-22T10:14:22Z"}
```

Если ожидалось `orders.created`, а виден `orders.us.created`, проблема в теме, а не интересе. Так находятся лишний сегмент и [пробел, незаметно меняющий маршрутизацию](/learn/core-nats/subjects-and-wildcards#pitfalls). Если при публикации ничего не видно, сообщение не покинуло издателя.

Перехват показывает и запросы с ответами, включая создаваемые клиентом темы [inbox](/learn/core-nats/request-reply#the-inbox): `_INBOX` — обычная тема протокола. Уже строки тем показывают полный обмен:

```text
[#2] Received on "orders.inventory.check" with reply "_INBOX.9tQ3pZ.aQ1"
[#3] Received on "_INBOX.9tQ3pZ.aQ1"
```

Сообщение №2 — запрос с темой ответа; №3 — ответ в этот inbox. Наличие обоих подтверждает полный обмен.

В активной учётной записи `>` создаёт большой трафик. Не успевающий подписчик отключается как медленный потребитель. Ограничьте наблюдение нужным семейством, например `orders.>`, чтобы видеть только важные темы.

## Список подписок на сервере {#list-the-subscriptions-the-server-holds}

Если сообщение ушло в правильную тему, но не пришло, проверьте интерес. Сервер хранит подписки в [графе интереса](/learn/core-nats/publish-subscribe#the-interest-graph) в памяти; нужно прочитать его.

На локальном сервере используйте обычный HTTP-[порт мониторинга](/learn/monitoring/monitoring-endpoints). Запустите сервер с `nats-server -m 8222`; `/subsz` перечисляет текущие подписки.

<div class="nats-example" data-type="learn-core-nats-debugging-delivery-list-subscriptions" data-languages="cli"></div>

`subs=1` добавляет `subscriptions_list`: для каждой подписки указаны учётная запись, тема и идентификатор соединения (`cid`). `acc=$G` ограничивает счётчики вашей учётной записью; без него `num_subscriptions` охватывает все, включая системную. Даже с ограничением список содержит служебные подписки `$SYS.REQ.*`, которые сервер держит в каждой учётной записи. Параметр `test` прямо отвечает на вопрос доставки: задайте точную тему публикации, и `/subsz` вернёт только подходящие подписки, включая шаблоны.

```json
{
  "num_subscriptions": 6,
  "total": 1,
  "offset": 0,
  "limit": 1024,
  "subscriptions_list": [
    { "account": "$G", "subject": "orders.>", "sid": "5", "msgs": 0, "cid": 8 }
  ]
}
```

Здесь `num_subscriptions` показывает шесть подписок учётной записи `$G`, а `total` — одну подходящую для `orders.us.created`: аудит `orders.>` на соединении `8`. Пустой `subscriptions_list` означает отсутствие подписчиков; публикация в этот момент будет отброшена. Для сохранения заказа до готовности подписчика нужен поток, добавляемый [JetStream](/learn/jetstream) поверх тех же тем.

Чтобы отличить отсутствующую подписку от разорванного соединения, посмотрите соединения. `/connz` перечисляет их, а `?subs=true` добавляет подписки каждого; подробно — на странице [точек мониторинга](/learn/monitoring/monitoring-endpoints). Если считающий себя подключённым подписчик отсутствует в `/connz`, соединение потеряно, а интерес удалён.

CLI `nats` читает то же состояние через NATS командами `nats server
request subscriptions` и `nats server request connections`. Обе используют запросы системной учётной записи `$SYS`. В обычном `nats-server` есть учётная запись `$SYS`, но нет её пользователя, а системные темы отвечают лишь подключённым к `$SYS` клиентам. Поэтому на локальном сервере `nats server request
subscriptions` выдаёт `server request failed, ensure the account used
has system privileges and appropriate permissions`. `nats server request
connections` отвечает, но показывает только соединения вашей учётной записи. Полный обзор сервера доступен с учётными данными [системной учётной записи](/learn/security), как в промышленных и кластерных развёртываниях.

## Трассировка пути одного сообщения {#trace-one-messages-path}

Перехват показывает темы, список подписок — интерес. **Трассировка сообщений** показывает оба аспекта для одной темы: всех подходящих подписчиков и переходы на пути к ним. Запустите `nats trace` с темой.

<div class="nats-example" data-type="learn-core-nats-debugging-delivery-trace-message" data-languages="cli"></div>

`nats trace` требует сервер NATS 2.11 или новее. Команда публикует специальное трассируемое сообщение и выводит рассчитанный сервером маршрут. Если подписчиков нет, трассировка сообщает об этом:

```text
Tracing message route to subject orders.us.created

Client "NATS CLI Version development" cid:16 server:"n1" version:"2.11.6"
--X No active interest

Legend: Client: --C Router: --> Gateway: ==> Leafnode: ~~> JetStream: --J Error: --X
```

При совпадении подписки строка `--C` указывает получателя и заканчивается совпавшей темой, например `subject:"orders.>"`. На каждого подходящего подписчика выводится одна `--C`, поэтому виден точный набор получателей настоящей публикации.

Трассировку безопасно выполнять в работающей системе: без `--deliver` сообщение не передаётся подходящим подписчикам. Она показывает возможных получателей без доставки и не запускает побочные эффекты. Добавляйте `--deliver` только для реальной доставки тестового сообщения.

## Выбор инструмента по симптому {#which-tool-answers-which-symptom}

Начните с наблюдаемого симптома и выберите средство проверки.

| Симптом | Инструмент |
|---|---|
| Неясно, покинуло ли сообщение клиента или какая тема использована | Перехват: `nats sub ">"`, затем публикация и наблюдение |
| Сообщение уходит, но ожидаемый подписчик ничего не получает | Список подписок: `/subsz?subs=1&acc=$G&test=<subject>` для проверки совпадений |
| Подписчик уверен в подписке, но ничего не получает | Соединения: `/connz?subs=true` для проверки открытого соединения |
| Нужен точный список возможных получателей публикации | Трассировка: `nats trace <subject>` |

Если `test=` и `nats trace` сейчас показывают подписчика, а сообщение не пришло, в момент публикации его не было. Это временное различие — [доставка не более одного раза](/learn/core-nats/publish-subscribe#at-most-once-delivery): Core NATS доставляет лишь подключённым в момент публикации и не повторяет попыток.

## Подводные камни {#pitfalls}

**Перехват `>` получает все сообщения рабочей учётной записи.** Он может не выдержать трафик и быть отключён как медленный потребитель. Ограничьте наблюдение нужным семейством, например `orders.>`, и длительностью исследования.

**Трассировка проверяет собственное сообщение, а не прошлую публикацию.** `nats
trace` отправляет новое сообщение и показывает его маршрут. Она ничего не доказывает о более раннем сообщении, а без `--deliver` вообще не достигает подписчиков. Читайте результат как ответ на вопрос «что было бы сейчас», а не «что произошло раньше».

**Порт мониторинга по умолчанию без аутентификации.** Любой имеющий доступ к `:8222` может прочитать темы и соединения через `/subsz` и `/connz`. На ноутбуке это допустимо, но не открывайте порт в общей или публичной сети. Защита описана в разделе [Безопасность](/learn/security); учитывайте её, чтобы не оставить порт открытым.

## Что уже сделано {#where-you-are}

Для каждой причины недоставки заказа Acme теперь есть инструмент:

- Перехват (`nats sub ">"`) показывает факт отправки и тему.
- Список подписок (`/subsz` с `test=` для точной темы) показывает подходящий интерес, а `/connz` — наличие соединения подписчика.
- Трассировка (`nats trace`) показывает точный список возможных получателей без доставки, если её явно не запросить.

Все три читают тот же граф интереса, которым сервер маршрутизирует сообщения, и показывают его вместо необходимости гадать.
