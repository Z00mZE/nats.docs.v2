# Подключение {#connecting}

Приложение NATS взаимодействует с сетью через **клиент**: встроенную в программу библиотеку или инструмент командной строки `nats`, который открывает соединение с сервером и передаёт по нему сообщения. Чтобы любой шаблон этой главы заработал, клиент должен подключиться. Эта страница посвящена самому соединению: что это, как его открыть и какие немногочисленные настройки выбрать.

Для главы нужен один работающий локальный `nats-server`. Стандартная сборка не требует конфигурации:

```bash
nats-server
```

Оставьте его работающим. Сервер слушает порт 4222, и все страницы этой главы используют его.

## Одно соединение для всех операций {#one-connection-carries-everything}

**Соединение** — одно долгоживущее TCP-соединение клиента с сервером. Клиент открывает его один раз при запуске приложения и сохраняет открытым до завершения работы приложения.

Все операции клиента проходят по этому соединению. Каждое опубликованное сообщение и каждая **подписка** (постоянный запрос на получение сообщений определённой темы) мультиплексируются в одном TCP-соединении и помечаются так, чтобы обе стороны различали потоки. Клиент не открывает новое соединение на каждую тему или сообщение: все они используют одно.

Поэтому следует подключаться один раз и повторно использовать результат. Одно соединение обслуживает тысячи подписок и высокую частоту сообщений. Клиенты рассчитаны на его совместное использование всеми операциями публикации и подписки.

## URL подключения {#the-connect-url}

Клиент устанавливает соединение по **URL подключения** — адресу сервера в формате `nats://host:port`. По умолчанию серверы слушают порт 4222, поэтому локальный сервер имеет адрес `nats://127.0.0.1:4222`. Этот адрес используется и клиентом без явно заданного URL, и CLI `nats`, пока вы не укажете другой через `--server` или сохранённый контекст.

Схема задаёт транспорт. `tls://` обозначает такое же соединение с шифрованием, а `ws://` и `wss://` передают протокол поверх WebSocket. Этот транспорт нужен браузеру и позволяет работать в сети, допускающей только исходящие подключения к порту 443. Подробнее — в разделе [Подключение через WebSocket](/learn/websocket/).

Один URL задаёт один сервер. В промышленной эксплуатации клиенту обычно передают несколько URL, чтобы он мог переключаться при недоступности сервера. Список и порядок перебора рассматриваются в разделе [Устойчивые клиенты → Подключение](/learn/resilient-clients/connecting). Здесь достаточно одного локального сервера.

## Обмен при установлении соединения {#the-connect-handshake}

После сетевого подключения клиент и сервер выполняют короткий **обмен при установлении соединения (handshake)** до передачи сообщений.

Первым отправляет сервер: он сразу передаёт `INFO` со сведениями о себе и ограничениях, включая `max_payload` (наибольший допустимый размер сообщения, по умолчанию 1 МБ) и поддержку заголовков сообщений. Клиент читает `INFO`, затем отвечает `CONNECT`, указывая имя, поддерживаемые возможности протокола и учётные данные. Сервер принимает параметры, и соединение готово передавать сообщения.

Первую половину обмена можно увидеть напрямую. Подключите к серверу любой инструмент для работы с TCP: сразу после подключения он выведет строку `INFO`:

## Имя соединения {#naming-the-connection}

Одно поле сообщения `CONNECT` стоит задать самостоятельно: **имя соединения**. По умолчанию клиент подключается без осмысленного имени, и мониторинг сервера показывает соединение без имени вообще (CLI `nats` подставляет общее `NATS CLI Version …`). Если задать имя, оно будет идентифицировать соединение.

CLI `nats` задаёт имя глобальным флагом `--connection-name`. Называйте соединение по сервису-владельцу. Здесь это `warehouse`, первый сервис Acme, который подключается и проверяет доступность сервера:

## Получение собственных сообщений {#receiving-your-own-messages}

Ещё одна настройка подключения — **echo**. По умолчанию соединение получает собственные сообщения: если клиент публикует в тему и одновременно подписан на неё, сервер отправляет ему копию так же, как остальным подписчикам.

Обычно это незаметно: клиент подписывается на темы, в которые публикуют другие. Настройка важна, когда один клиент и публикует обновления в тему, и слушает её: он получает собственную публикацию. Отключение echo при подключении (опция `NoEcho` в клиентах) указывает серверу пропускать исходное соединение при доставке, чтобы клиент не получал свои сообщения. Как и имя, настройка действует весь срок жизни соединения и выбирается при его открытии.

## Проверка соединения с помощью PING/PONG {#staying-connected-with-pingpong}

Открытое соединение может простаивать между сообщениями. Чтобы заметить отключение, сбой или потерю сетевой связи на другой стороне, не дожидаясь ошибки очередной отправки, обе стороны обмениваются heartbeat.

Механизм называется **PING/PONG**. Каждая сторона периодически отправляет `PING` и ждёт `PONG`. Если слишком много PING остаётся без ответа, сторона считает партнёра недоступным и закрывает соединение. Клиент и сервер делают это независимо, поэтому отказ может обнаружить любая сторона. Значения по умолчанию одинаковы: PING раз в две минуты, соединение считается потерянным после двух PING без ответа.

Выполненная выше команда `nats rtt` запускает этот обмен по требованию. Каждый измеренный цикл — это `PING` серверу и ответный `PONG`. По умолчанию усредняются пять таких измерений.

Heartbeat лишь обнаруживает разрыв. Восстановление через переподключение и буферизацию публикаций во время отключения описано далее в разделе [Жизненный цикл соединения](/learn/core-nats/connection-lifecycle), а производственные настройки — в [Устойчивые клиенты → Переподключение](/learn/resilient-clients/reconnection).

## Подводные камни {#pitfalls}

**Новое соединение на каждое сообщение.** Соединение предназначено для однократного открытия и совместного использования. Если подключаться, публиковать одно сообщение и отключаться, весь handshake повторяется каждый раз, а соединение, рассчитанное на тысячи сообщений, выбрасывается. Открывайте одно соединение при запуске сервиса и используйте его для всех публикаций и подписок.

**Клиент, публикующий и подписанный на одну тему, получает собственные сообщения.** При включённом echo (по умолчанию) публикации клиента возвращаются его подходящим подпискам. Если это не нужно, открывайте соединение с отключённым echo (`NoEcho`), чтобы исходное соединение пропускалось.

**Завершение до отправки буферизованных публикаций.** Публикация помещает сообщение в буфер записи клиента и сразу возвращает управление. Короткоживущая программа может завершиться до передачи буфера серверу. Перед выходом выполняйте flush. Подробности — в [разделе о подводных камнях публикации и подписки](/learn/core-nats/publish-subscribe#pitfalls): этот буфер используется и для одного сообщения, и для многих.

## Что уже сделано {#where-you-are}

Теперь в примере Acme есть работающий сервер и клиент, способный к нему подключиться:

- Один локальный `nats-server` работает на `nats://127.0.0.1:4222`.
- Вы понимаете соединение как одно долгоживущее TCP-соединение для всех публикаций и подписок.
- Оно открывается по URL; до передачи сообщений сервер отправляет `INFO`, а клиент — `CONNECT`.
- Соединение `warehouse` имеет имя, заданное через `--connection-name`, по которому сервер может его определить.
- Echo по умолчанию возвращает клиенту его сообщения, а heartbeat `PING`/`PONG` помогает обеим сторонам заметить недоступного партнёра.

## Что дальше {#whats-next}

Соединение открыто. Теперь используйте его: опубликуйте сообщение в тему, чтобы другие клиенты получили копию. Раздел [Публикация и подписка](/learn/core-nats/publish-subscribe) знакомит с базовой операцией Core NATS и графом интереса, определяющим получателей каждого сообщения.
