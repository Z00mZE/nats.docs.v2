# Заголовки сообщений {#message-headers}

До сих пор сообщение состояло из темы и полезной нагрузки. NATS позволяет добавить третью часть: **заголовки**, метаданные «ключ — значение», передаваемые рядом с нагрузкой. Тело содержит бизнес-данные, а заголовок сообщает сведения о них без чтения тела: отправителя, формат или идентификатор трассировки.

Один заголовок вы уже видели: при [отсутствии отвечающих сервисов](/learn/core-nats/request-reply#no-responders) сервер отвечает заголовком без полезной нагрузки. Здесь разберём весь механизм.

## Формат заголовков {#the-header-format}

Блок заголовков текстовый и похож на HTTP. Он начинается со строки версии `NATS/1.0`, затем идут пары `Key: Value`, каждая с новой строки:

```
NATS/1.0
Content-Type: application/json
Acme-Request-Id: req_7f3c9a
```

Каждая пара содержит один ключ и значение. Ключ может повторяться в нескольких строках для передачи нескольких значений; получатель читает их все. Поэтому заголовок фактически сопоставляет ключ списку значений, хотя чаще в списке одно.

NATS сохраняет регистр ключей и различает его: `Content-Type` и `content-type` — разные ключи. Многие библиотеки HTTP приводят ключи к единому регистру, но NATS этого не делает. Выберите одно написание и используйте на обеих сторонах.

Блок заголовков передаётся с сообщением, но отдельно от нагрузки, поэтому получатель читает ровно те байты тела, которые опубликованы. Игнорирующий заголовки сервис видит тот же JSON, что и раньше.

Библиотеки предоставляют тип заголовков сообщения. `Set` задаёт значение ключа, `Add` добавляет ещё одно; `Get` читает первое, а `Values` — весь список.

`Content-Type` из примера — почти повсеместный заголовок: он указывает, как читать тело, здесь `application/json`. Остальные ключи выбираете вы. Не используйте собственные ключи с префиксом `Nats-`: он зарезервирован для системных заголовков. Некоторые управляют [JetStream](/learn/jetstream) и выходят за рамки Core NATS.

## Идентификаторы запроса и трассировки {#a-request-id-and-a-trace-id}

Запрос-ответ естественно сочетается с заголовками. Когда склад спрашивает сервис наличия, [есть ли товар](/learn/core-nats/request-reply), вопрос и ответ — два сообщения. Заголовки позволяют пометить их без изменения данных заказа.

Добавьте `Acme-Request-Id` для отдельного вызова и `Acme-Trace-Id` — **идентификатор корреляции**, общий для сообщений одной логической операции. Так можно проследить заказ между сервисами. Отвечающий сервис читает trace ID из запроса и копирует в ответ:

## Коды состояния сервера {#status-codes-from-the-server}

Сервер тоже использует заголовки. Он передаёт клиенту **код состояния** в строке версии внутри того же канала. Вместо одного `NATS/1.0` строка содержит `NATS/1.0 503`, а полезная нагрузка отсутствует.

Вы уже встречали это: [no responders](/learn/core-nats/request-reply#no-responders) — ответ со строкой `NATS/1.0 503` и пустым телом. Клиент распознаёт код и возвращает отдельную ошибку. Весь механизм — статус в заголовке без нагрузки, прочитанный клиентом ещё до передачи сообщения вашему коду.

## Поддержка заголовков согласуется при подключении {#header-support-is-negotiated-at-connect}

Заголовки работают при согласии обеих сторон, которое устанавливается при открытии соединения. Сервер объявляет поддержку полем `headers` в первоначальной строке INFO; по умолчанию она включена. Клиент читает её и сообщает свою поддержку в ответном CONNECT. До первой публикации обе стороны уже знают о заголовках.

Современные серверы и клиенты поддерживают заголовки, поэтому согласование незаметно. Сбой возможен при `no_header_support` в конфигурации сервера или слишком старом сервере. Тогда клиент не видит объявления поддержки и отклоняет публикацию с заголовком ошибкой `headers not supported by this server` до отправки сообщения. Обмен INFO и CONNECT разобран на странице [Подключение](/learn/core-nats/connecting).

Это согласование относится и к предыдущему разделу: без поддержки заголовков соединение не может получить сигнал no responders.

## Попробуйте {#try-it}

Откройте два терминала, подключённых к работающему серверу.

```bash
# Terminal 1 — watch orders.created with headers rendered
nats sub orders.created
```

```bash
# Terminal 2 — publish an order tagged with a content type and a request ID
nats pub orders.created \
  '{"order_id":"ord_8w2k","customer":"acme-co","total_cents":4200,"ts":"2026-05-22T10:14:22Z"}' \
  -H 'Content-Type:application/json' \
  -H 'Acme-Request-Id:req_7f3c9a'
```

Первый терминал выведет заголовки над телом; две строки заголовков могут идти в любом порядке:

```
[#1] Received on "orders.created"
Content-Type: application/json
Acme-Request-Id: req_7f3c9a

{"order_id":"ord_8w2k","customer":"acme-co","total_cents":4200,"ts":"2026-05-22T10:14:22Z"}
```

Теперь добавьте подписчику `--headers-only` и повторите публикацию. Вы получите строки заголовков без тела — удобный способ изучить метаданные активной темы без вывода каждой нагрузки.

## Подводные камни {#pitfalls}

**Неверный регистр ключа.** Ключи чувствительны к регистру. Если издатель отправляет `Content-Type`, а вы читаете `content-type`, результат пустой и ошибки нет. Используйте точное написание отправителя и единое соглашение между сервисами.

**Заголовки входят в лимит нагрузки.** Сервер сверяет общий размер заголовков и тела с `max_payload` — тем же пределом 1 МБ, что действует для [самой нагрузки](/learn/core-nats/publish-subscribe#the-1-mb-payload-limit). Большие заголовки оставляют меньше места телу; при превышении общего лимита публикация отклоняется.

**Бизнес-данные в заголовках.** Заголовки предназначены для небольших метаданных: идентификатора, типа содержимого, флага. Большие и структурированные данные должны находиться в теле, где их ждёт получатель. Такие данные в заголовках увеличивают сообщения и конкурируют с телом за `max_payload`. Делайте заголовки короткими, а тело — основным источником данных.

## Что уже сделано {#where-you-are}

В примере Acme сообщения теперь имеют метаданные рядом с нагрузкой:

- Издатель добавляет заголовки через `-H` или клиентские `Set`/`Add`, подписчик читает через `nats sub` или `Get`/`Values`.
- Запрос содержит идентификаторы запроса и трассировки; сервис копирует trace ID в ответ для корреляции.
- Сервер также использует заголовки в том же канале, передавая сигнал no responders как `NATS/1.0 503`.
- Поддержка заголовков согласуется при подключении и есть во всех современных серверах и клиентах.

## Что дальше {#whats-next}

Заголовки следуют вместе с сообщением туда, куда ведёт тема. Иногда нужно изменить адрес: переписать тему при входе на сервер, чтобы `orders.created` могло приходить под другим именем без ведома издателя.
