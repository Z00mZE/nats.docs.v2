# Запрос-ответ {#request-reply}

Публикация и подписка однонаправленны. Издатель публикует в `orders.created`, и каждый заинтересованный подписчик получает копию. Издатель ничего не получает в ответ.

Acme нужно и обратное направление. Когда поступает заказ, склад хочет задать вопрос и получить ответ: _есть ли этот товар в наличии?_ Это запрос и ответ, а не рассылка.

На этой странице вы создадите сервис **inventory**, отвечающий на вопрос в теме `orders.inventory.check`. По ходу разберём две основы запроса и ответа: приватную тему ответа, создаваемую клиентом для себя, и поведение при отсутствии отвечающего сервиса.

## Как запрос-ответ использует публикацию и подписку {#how-request-reply-uses-pubsub}

Запрос-ответ — не новый протокол, а два применения уже знакомой публикации и подписки.

Последовательность такова. Клиент создаёт новую уникальную тему для ответа и подписывается на неё. Затем публикует запрос, указывая тему ответа в поле сообщения. Отвечающий сервис читает запрос, видит тему ответа и публикует туда результат. Подписка клиента получает его.

<div class="nats-flow" data-scenario="requestReply" data-width="800" data-height="350"></div>

Оранжевая стрелка — запрос, уходящий в тему запросов. Зелёная пунктирная — ответ, возвращающийся в приватную тему, которую клиент создал для этого вызова.

Каждый клиент NATS объединяет эти шаги в один вызов `request()`: подписку, публикацию и ожидание не нужно писать вручную.

## Inbox {#the-inbox}

Приватная тема ответа называется **inbox**. Клиенты создают её с зарезервированным префиксом `_INBOX.`, например `_INBOX.nQ4k2v8...` со случайным уникальным окончанием.

Inbox индивидуален для запроса: каждый `request()` использует новый, поэтому параллельные запросы не получают чужие ответы. Префикс `_INBOX.` зарезервирован и не пересекается с выбранными вами темами: этим пространством управляет клиент.

Клиент не открывает отдельную подписку для каждого `request()`. При первом запросе он один раз подписывается на постоянный для соединения шаблон вида `_INBOX.<connection>.*` и использует подписку для последующих запросов. Запрос добавляет к префиксу только свой последний сегмент. Новый inbox на запрос фактически означает новый сегмент, а клиент направляет ответ тому запросу, который ждёт этот сегмент.

Поэтому тысячи параллельных запросов требуют одной подписки: все ответы приходят по одному шаблону, а последний сегмент определяет запрос. Клиенты можно настроить на отдельную подписку для каждого запроса, но по умолчанию используется общая.

Длина темы ответа ограничена. Сервер по умолчанию ограничивает одну строку протокола, включая тему и тему ответа, 4 КБ (`max_control_line`). Автоматические имена inbox намного короче; ограничение важно лишь при ручном создании необычно длинных тем.

Стандартный префикс `_INBOX.` настраивается для соединения через клиентскую опцию, представленную в natscli глобальным флагом `--inbox-prefix`. Это нужно для разрешений: отдельный префикс приложения позволяет оператору выдать ему собственное пространство ответов вместо общего `_INBOX.>`. Разрешения на темы разобраны в разделе [Авторизация](/learn/security/authorization).

## Сервис наличия товаров {#the-inventory-service}

Теперь создайте реальный отвечающий сервис. Он подписывается на `orders.inventory.check` и отвечает на каждый запрос сведениями о наличии товара.

В CLI команда `nats reply` именно это и делает: подписывается на тему, входя в стандартную группу очереди `NATS-RPLY-22`, и публикует ответ в inbox, указанный каждым запросом.

## Каждому запросу нужен тайм-аут {#every-request-needs-a-timeout}

Ответ может не прийти: сервис занят, работает медленно или ответ потерялся в пути. Ответы, как и всё остальное, доставляются [не более одного раза](/learn/core-nats/publish-subscribe#at-most-once-delivery): неполученный ответ потерян и не отправляется повторно.

Поэтому каждому запросу задаётся **тайм-аут** — максимальное время ожидания ответа. CLI задаёт `--timeout` автоматически (пять секунд по умолчанию), а пример выше явно использует `--timeout 2s`. Выберите время, покрывающее обработку и сетевой обмен. В клиентской библиотеке тайм-аут передаётся каждому `request()`, чтобы запрос не ждал бесконечно.

Если время истекло без ответа, вызов возвращает ошибку тайм-аута. Код приложения решает, что делать дальше: повторить, использовать запасной вариант или вернуть ошибку вызывающему. Core NATS не принимает это решение и не доставляет ответ с опозданием.

Тайм-аут означает, что ответ не пришёл вовремя, но не объясняет _почему_: сервис может работать медленно или отсутствовать. Следующий раздел различает эти случаи.

## Нет отвечающих сервисов {#no-responders}

Ждать две секунды лишь для обнаружения отсутствия слушателей неэффективно. Для этого случая у NATS есть более быстрый сигнал.

Если запрос отправлен в тему без подписчиков, сервер сразу знает, что ответить некому. Вместо ожидания тайм-аута он немедленно возвращает сигнал **no responders**: ответ со статусом `503`. Клиент представляет его отдельной ошибкой отсутствия отвечающих сервисов, а не тайм-аутом.

Так различаются «сервис наличия товаров работает медленно» (тайм-аут через 2 секунды) и «сервис вообще не запущен» (no responders за миллисекунды). Первое — проблема задержки, второе — развёртывания. Сигнал позволяет коду реагировать по-разному.

Проверьте сами. Остановите сервис в первом терминале, затем повторите запрос:

```bash
nats request orders.inventory.check \
  '{"order_id":"ord_8w2k","customer":"acme-co","total_cents":4200,"ts":"2026-05-22T10:14:22Z"}' \
  --timeout 2s
```

```
14:02:31 Sending request on "orders.inventory.check"
14:02:31 No responders are available
```

Сигнал отсутствия отвечающих сервисов возвращается сразу, а не через две секунды. CLI выводит строку и корректно завершается; библиотека возвращает отдельную ошибку для ветвления кода (`ErrNoResponders` в Go, с аналогами в других языках). Запустите сервис снова — тот же запрос будет успешен.

Сигнал использует заголовки сообщений: сервер отправляет ответ со строкой заголовка `NATS/1.0 503`. Для его получения клиент должен поддерживать заголовки; современные клиенты включают эту поддержку.

## Заголовки {#headers}

Механизм `503` показывает более широкую возможность: сообщения NATS могут содержать **заголовки** — метаданные «ключ — значение» рядом с полезной нагрузкой в формате, похожем на HTTP. Их может добавлять как запрос, так и ответ.

Для проверки наличия товара заголовки не нужны, поэтому здесь мы их не используем. Запись и чтение описаны в разделе [Заголовки сообщений](/learn/core-nats/headers), полный формат — в [Справочнике](/reference/). Используйте заголовки для метаданных вне бизнес-нагрузки: идентификатора запроса, контекста трассировки или типа содержимого.

## Запрос-ответ, группы очередей и несколько ответов {#request-reply-queue-groups-and-many-answers}

В сервисе наличия товаров один отвечающий процесс. Естественно возникают два вопроса, каждому посвящена отдельная страница.

Что, если запустить несколько экземпляров для производительности и поручать каждый запрос ровно одному? Это **группа очереди**, которую создаёт [следующая страница](/learn/core-nats/queue-groups).

Что, если на один запрос должны ответить _все_ сервисы темы, а вы соберёте ответы? Это [scatter-gather](/learn/core-nats/scatter-gather), который разбирается через страницу.

Если сервисам запрос-ответ нужны полноценные конечные точки, обнаружение и статистика, используйте [фреймворк сервисов](/learn/services). Этот слой построен именно на примитивах запроса-ответа и групп очередей из текущей главы. Здесь мы остаёмся на уровне примитивов.

## Подводные камни {#pitfalls}

**Запрос без тайм-аута может ждать бесконечно.** Ограничивайте каждый `request()` сроком, достаточным для работы сервиса и сетевого обмена, чтобы не отказываться от просто медленного ответа.

**Не считайте no responders зависанием.** Сигнал приходит за миллисекунды, а не после долгого тайм-аута. Обрабатывайте его отдельно: no responders означает отсутствие развёрнутого сервиса, тайм-аут — медленную работу существующего.

**Не предполагайте, что ответ ровно один.** Обычный `request()` возвращает первый ответ и отбрасывает остальные. Если два экземпляра отвечают в `orders.inventory.check`, второй ответ молча теряется без уведомления о его поступлении. Когда ответить может больше одного сервиса, явно запросите несколько ответов и собирайте их по числу или сроку:

Когда нужны ответы всех сервисов, это [scatter-gather](/learn/core-nats/scatter-gather), а не ошибка. Когда один запрос должен обработать один из нескольких экземпляров, нужна [группа очереди](/learn/core-nats/queue-groups).

**Медленная работа внутри отвечающего сервиса.** Долгий поиск перед ответом задерживает следующие запросы: один дорогой вызов добавляет задержку всем ожидающим. Держите путь ответа быстрым или запустите несколько экземпляров в [группе очереди](/learn/core-nats/queue-groups), распределяя нагрузку вместо её накопления на одном процессе.

## Что уже сделано {#where-you-are}

В примере Acme появился первый двусторонний обмен:

- Сервис наличия товаров отвечает на `orders.inventory.check` через `nats reply` или клиентский `respond()`.
- Склад задаёт вопросы через `nats request` или `request()`, ограничивая каждый вызов тайм-аутом.
- Отсутствие сервиса обнаруживается сразу как no responders, а не долгий тайм-аут.
- Ответы доставляются не более одного раза, как всё в Core NATS: без повторов и хранения.

## Что дальше {#whats-next}

Сервис наличия товаров — один процесс. Для масштабирования запустите несколько копий и позвольте NATS передавать запрос ровно одной. Это группа очереди: встроенная балансировка нагрузки без промежуточной очереди брокера. Создайте её на следующей странице: [Группы очередей](/learn/core-nats/queue-groups).
