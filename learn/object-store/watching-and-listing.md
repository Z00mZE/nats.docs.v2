# Наблюдение и список объектов {#watching-and-listing}

В `INVOICES` уже несколько объектов: `invoice-ord_8w2k.pdf` с описанием и `content-type`, крупный `invoice-ord_9x3m.pdf` из многих фрагментов и ссылка `label-ord_8w2k.png` на первый счёт. Для get нужно знать имя. Но `analytics` не знает имён заранее: ему нужно обнаружить содержимое и узнавать о новых объектах сразу после записи.

Для этого есть две операции. List получает снимок всех текущих объектов, watch передаёт обновления метаданных по мере возникновения. Так `analytics` узнаёт о счёте сразу после put от `order-svc`, не зная заранее содержимого бакета.

## List возвращает снимок {#list-is-a-snapshot}

**List** однократно возвращает все неудалённые объекты. Он не остаётся открытым и не передаёт последующие изменения: отвечает на вопрос о текущем содержимом и завершается.

Выполните его для `INVOICES`:

<div class="nats-example" data-type="learn-object-store-watching-and-listing-list" data-languages="cli,js,go,python,java,rust,csharp"></div>

Результат содержит по записи для `invoice-ord_8w2k.pdf`, `invoice-ord_9x3m.pdf` и `label-ord_8w2k.png`. В каждой — метаданные: имя, размер, число фрагментов, описание, время изменения. Байтов нет. List читает только метаданные; можно перечислить гигабайтные счета без передачи содержимого объектов.

Мягко удалённые объекты пропускаются. Когда `order-svc` удаляет счёт, ставится признак удаления и очищаются фрагменты, но метаданные остаются как маркер. List отфильтровывает их, показывая только существующие объекты. Механизм рассматривается в разделе [Внутреннее устройство](/learn/object-store/under-the-hood); здесь важно поведение.

Пустой бакет не является ошибкой. Список нового бакета возвращает пустой результат. Клиентские библиотеки сообщают отдельное состояние отсутствия объектов, которое следует понимать как ноль результатов, а не неполадку. Пример приведён ниже.

## Watch передаёт изменения метаданных {#watch-streams-metadata-updates}

**Watch** — непрерывный аналог list: открывает поток метаданных и передаёт обновление при каждом изменении объекта, будь то первый put, повторный put или удаление. Так `analytics` следит за бакетом без циклического вызова list.

Запустите `analytics` для наблюдения за `INVOICES` в отдельном терминале и оставьте работать:

<div class="nats-example" data-type="learn-object-store-watching-and-listing-watch" data-languages="cli,js,go,python,java,rust,csharp"></div>

Обновления приходят в порядке записи бакетом, поэтому позднее состояние не опережает раннее. После получения всего уже существующего watch передаёт один **маркер nil** — пустое обновление, обозначающее переход к текущим изменениям. CLI обрабатывает его автоматически и продолжает вывод. В коде нужно распознать границу и продолжить чтение.

В другом терминале пусть `order-svc` запишет упаковочный лист того же заказа:

```bash
echo "PACK ord_8w2k: 3 items" | nats object put INVOICES --name packing-slip-ord_8w2k.txt
```

Обновление появляется сразу после put, без опроса и задержки. `analytics` узнаёт о `packing-slip-ord_8w2k.txt`, как только `order-svc` сохраняет его.

<div class="nats-flow" data-scenario="objectWatchSyncAnimated" data-width="600" data-height="350"></div>

Обновление содержит только *метаданные* объекта: имя, размер, число фрагментов и хеш. Байты через watch не передаются. Это его важнейшее свойство.

## Watch передаёт метаданные без содержимого {#watch-carries-metadata-never-the-bytes}

Метаданные и фрагменты объекта находятся в разных темах. Watch подписывается на метаданные, поэтому каждое обновление — запись `ObjectInfo`, а не байты объекта.

Это позволяет наблюдать недорого. `analytics` следит за счетами на 3 МБ и медиафайлами на 100 МБ без передачи их содержимого. Он узнаёт об изменении и свойствах; при необходимости запрашивает данные отдельным get.

Шаблон двухэтапный: узнать изменение через watch, затем получить нужные байты через get. Для панели `analytics` может хватить метаданных без чтения содержимого. Сервис повторной обработки, наоборот, получает каждый новый объект. Наблюдение одинаково, различается лишь выполнение второго шага.

Это отличие от наблюдения в KV: там передаётся само *значение* небольшого ключа. Объект может занимать гигабайты, поэтому watch оставляет загрузку вам. См. [Ключи и значения → Наблюдение](/learn/key-value/watching). Для объектов watch сообщает об изменении, get возвращает байты.

Дополнительные параметры позволяют воспроизводить историю, игнорировать удаления или пропускать начальный снимок ради только новых обновлений. Они настраивают тот же поток метаданных. Все параметры приведены в [справочнике](/reference/); здесь достаточно стандартного поведения.

## Подводные камни {#pitfalls}

При чтении неизвестного содержимого бакета распространены две ошибки: непонимание результата list и данных watch.

**Watch передаёт метаданные, а не байты.** Обновление — запись `ObjectInfo` с именем, размером, числом фрагментов и хешем. Сервис, принимающий её за файл и ожидающий полезную нагрузку на 100 МБ, получит лишь метаданные и сломается. Используйте два шага: watch сообщает, *что* изменилось, get читает нужные объекты. Не ждите содержимого от наблюдения.

**Пустой бакет даёт пустой результат, а не ошибку.** List без живых объектов возвращает ноль записей. Библиотеки выделяют состояние отсутствия объектов; если считать его фатальным, программа упадёт на пустом бакете или после удаления всех объектов. Принимайте пустой список как корректный ответ «пока ничего нет». Отсутствие объектов и отсутствие самого бакета — разные состояния; проблема лишь во втором.

## Текущее состояние {#where-you-are}

Теперь у вас есть:

- Список `INVOICES`: метаданные `invoice-ord_8w2k.pdf`, `invoice-ord_9x3m.pdf` и `label-ord_8w2k.png`, без мягко удалённых объектов.
- `analytics`, наблюдающий за бакетом и получивший текущее обновление добавленного `packing-slip-ord_8w2k.txt`.
- Двухэтапная модель: watch сообщает об изменении, get получает байты.
