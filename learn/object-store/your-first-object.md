# Первый объект {#your-first-object}

Сервис Acme `order-svc` уже публикует сообщения заказов в поток `ORDERS`. Но заказ создаёт не только сообщение: после оплаты появляется PDF счёта, слишком крупный и двоичный для полезной нагрузки сообщения. Его нужно сохранить, а сервису `warehouse` — получить перед отправкой коробки.

Для этого предназначено **хранилище объектов**. Здесь создадим первый бакет Acme, сохраним счёт и прочитаем его обратно. Рассмотрим две операции: `put` и `get`.

## Бакет хранит объекты {#a-bucket-holds-objects}

**Бакет** — именованное хранилище объектов. **Объект** — один сохранённый файл: имя и байты. Бакет этой главы называется `INVOICES` и хранит PDF счетов заказов Acme.

За бакетом стоит поток JetStream, такой же, как в [углублённом курсе JetStream](/learn/jetstream). Создавать его самостоятельно не нужно: он появляется вместе с бакетом. Всё известное о потоках по-прежнему действует на нижнем уровне; глава ссылается на эти знания вместо повторного объяснения.

## Put: сохранение имени и байтов {#put-store-a-name-and-bytes}

**Put** записывает объект. Вы передаёте имя и байты, а хранилище сохраняет их. Байты могут поступать из файла на диске, из памяти или из постепенно читаемого потока данных. Каждый клиент предоставляет удобные варианты.

Внутри одного вызова происходят три действия. Сначала байты разбиваются на части, каждая становится отдельным сообщением. Подробности — на [следующей странице](/learn/object-store/chunking); пока достаточно понимать, что большой файл не превращается в одно гигантское сообщение.

Во-вторых, по мере поступления байтов вычисляется **хеш SHA-256** — отпечаток фиксированного размера для точной последовательности записанных байтов. Это односторонний хеш: одинаковые байты дают одинаковый результат, изменение байтов меняет результат.

В-третьих, после сохранения байтов записываются итоговые метаданные объекта: имя, размер, число частей и хеш. При get важен именно хеш.

**Get** получает объект. Вы указываете имя и получаете байты. Сервис `warehouse` читает счёт, необходимый для отправки `ord_8w2k`:

<div class="nats-example" data-type="learn-object-store-your-first-object-get" data-languages="cli,js,go,python,java,rust,csharp"></div>

Перед возвратом get проверяет байты. Хранилище читает метаданные, получает части по порядку, собирает их и заново вычисляет SHA-256. Байты возвращаются только при совпадении с хешем, записанным при put. Если часть потеряна или передача оборвалась, get возвращает ошибку, а не повреждённый файл.

Контракт хранилища таков: вы получаете в точности записанные байты либо ошибку. Незаметно обрезанный файл не возвращается.

## Путь записи и чтения {#watch-put-and-get-flow}

Анимация показывает полный цикл. При put сервис `order-svc` отправляет части и затем метаданные в `INVOICES`. При get `warehouse` сначала читает метаданные, затем получает части по порядку, собирает и проверяет хеш перед возвратом счёта.

Put записывает части, затем метаданные. Get читает метаданные, затем части и выполняет проверку. Этот порядок позволяет узнать ожидаемое число частей и хеш для сравнения.

## Подводные камни {#pitfalls}

При работе с первым объектом распространены две ошибки. Обе возникают, если считать put и get безотказными.

**При несовпадении хеша байты использовать нельзя.** Метаданные записываются после частей, поэтому прерванный put из-за завершения процесса или разрыва соединения вообще не оставляет доступного объекта: get сообщает об отсутствии имени, а не возвращает повреждённый файл. Несовпадение хеша — другой сбой: объект был сохранён целиком, но части позднее потерялись или повредились. Get сравнивает собранные байты с хешем и возвращает `ErrDigestMismatch`. Игнорировать эту ошибку и использовать данные нельзя. Проверяйте результат; при `ErrDigestMismatch` повторите get. Повторное несовпадение означает повреждение объекта и необходимость нового put. Не считайте запись успешной без подтверждённого чтением полного цикла.

**Отсутствующий объект — ошибка, а не пустые байты.** Для никогда не записанного или удалённого имени get возвращает ошибку отсутствия, а не пустой файл. Сервис `warehouse` должен отдельно обрабатывать отсутствие счёта: возможно, он ещё не создан. Проверяйте этот случай, повторяйте запрос или ждите; отсутствие счёта нельзя считать пустым счётом и продолжать отправку.

## Текущее состояние {#where-you-are}

Теперь у вас есть:

- Бакет `INVOICES` на основе автоматически созданного потока JetStream.
- Объект `invoice-ord_8w2k.pdf`, записанный сервисом `order-svc`.
- Тот же счёт, прочитанный сервисом `warehouse` с проверкой SHA-256.

Сеанс продолжается. Следующие страницы развивают этот бакет, а не создают всё заново.
