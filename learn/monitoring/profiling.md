# Профилирование сервера {#profiling-the-server}

Все предыдущие показатели сообщают, *что* делает кластер `east`: сколько клиентов у `n1-east`, насколько отстал `shipping`, сколько памяти занял процесс. Но они не показывают, *где* внутри сервера расходуются память и процессорное время. Это задача профиля.

Профилирование дополняет четыре способа наблюдения из этой главы. Оно нужно, когда `/varz` показывает рост кучи `n1-east` без изменения трафика или полную загрузку ядра, которую не объясняют панели Grafana. Это инструмент разработки и поддержки: вы снимаете профиль, читаете его через `go tool pprof` и часто передаёте тому, кто отлаживает сервер. Для повседневной статистики продолжайте пользоваться [портом мониторинга](/learn/monitoring/monitoring-endpoints).

Вы получите профиль двумя способами: через системную учётную запись командой CLI `nats` и через собственный HTTP-порт профилирования сервера. Оба дают одинаковый файл pprof.

## Профиль — выборка работающего процесса {#a-profile-is-a-sample-of-the-running-process}

**Профиль** — выборка, которую среда выполнения Go снимает внутри процесса сервера. Результат имеет двоичный формат **pprof**, читаемый [`go tool pprof`](https://pkg.go.dev/net/http/pprof). Каждый вид профиля отвечает на свой вопрос; выбор зависит от симптома:

| Профиль | Содержимое | Когда нужен |
|---|---|---|
| `heap` | Только живые объекты | Память растёт, и нужно понять, что её удерживает |
| `allocs` | Все выделения памяти с запуска, включая уже освобождённые | Интенсивные выделения и освобождения: нужно найти основной источник |
| `goroutine` | Стек каждой текущей горутины | Сервер выглядит зависшим или число горутин растёт |
| `cpu` | Стеки, собранные за фиксированный интервал | Узел полностью загружает ядро |

Сервер также предоставляет `block`, `mutex` и `threadcreate`. Для содержимого `block` нужно заранее включить сбор (см. [Типичные ошибки](#pitfalls)); два других редко нужны в первую очередь.

Профили памяти и горутин возвращаются сразу: данные уже есть у среды выполнения. Профилю CPU нужно некоторое время наблюдать процесс, поэтому запрос ждёт весь интервал сбора и затем возвращается.

## Запросите профиль через системную учётную запись {#request-a-profile-over-the-system-account}

`nats server request profile` запрашивает профили работающих серверов и записывает каждый ответ в файл. Запрос идёт в `$SYS.REQ.SERVER.PING.PROFILEZ`, поэтому контекст должен подключаться к **системной учётной записи**. Обычная запись вроде `ACME` не имеет прав на `$SYS` и не получит ответов.

<div class="nats-example" data-type="learn-monitoring-profiling-requestProfile" data-languages="cli"></div>

Каждый ответивший сервер создаёт отдельный файл `<profile>-<timestamp>-<server>` в рабочем каталоге:

```text
Server "n1-east" profile written: heap-20260824-141530-n1-east
Server "n2-east" profile written: heap-20260824-141530-n2-east
Server "n3-east" profile written: heap-20260824-141530-n3-east
```

Это не меняет конфигурацию и не требует перезапуска, поэтому сначала пробуйте этот способ.

### Ограничьте запрос нужными серверами {#narrow-the-request-to-specific-servers}

Запрашивать профиль всей системы нормально для трёх узлов, но расточительно для большого кластера. Флаги `--name`, `--host`, `--cluster` и `--tags` ограничивают отвечающие серверы; их можно сочетать.

### Профилю CPU нужен интервал сбора {#cpu-profiles-need-a-sampling-window}

Для `cpu` CLI использует глобальный флаг `--timeout` как длительность сбора. По умолчанию это `5s`, поэтому `nats server request profile cpu` снимает выборки пять секунд. Сервер отклоняет интервал длиннее **15 секунд**, возвращая ошибку вместо профиля. Более длительную запись нужно получать через порт профилирования ниже.

## Или включите порт профилирования {#or-expose-the-profiling-port}

Сервер может предоставлять обработчики Go `net/http/pprof` на отдельном порту. Он выключен, пока вы не зададите `prof_port` в конфигурации узла:

```conf
prof_port: 65432
```

`prof_port` не поддерживает перечитывание конфигурации: SIGHUP его не включит, нужен перезапуск узла. См. [Справочник → prof_port](/reference/config/prof_port) и [Управление конфигурацией](/learn/deployment/config-management) о возможностях и ограничениях SIGHUP.

После запуска слушателя `http://localhost:65432/debug/pprof/` перечисляет доступные профили; каждый можно скачать по обычному HTTP:

```bash
# Live heap, returns immediately.
curl -o heap.prof http://localhost:65432/debug/pprof/heap

# CPU sampled for 30 seconds; the request blocks for that long.
curl -o cpu.prof "http://localhost:65432/debug/pprof/profile?seconds=30"
```

Предел 15 секунд относится к обработчику системной учётной записи, а не к `pprof`, поэтому здесь `?seconds=` допускает более длительный интервал.

## Прочитайте профиль {#read-the-profile}

Оба способа дают одинаковый файл pprof, читаемый `go tool pprof`. Текстовая сводка самых затратных мест вызовов:

```bash
go tool pprof -top heap-20260824-141530-n1-east
```

Либо интерактивное веб-представление с пламенными диаграммами и деревом вызовов:

```bash
go tool pprof -http=:8080 cpu.prof
```

Если профиль предназначен другому специалисту, эти шаги не нужны: передайте сам файл.

## Типичные ошибки {#pitfalls}

При первом профилировании рабочего узла часто встречаются три проблемы. Все связаны с двумя способами доступа: запросом через системную учётную запись и портом профилирования.

**У порта профилирования нет аутентификации.** Любой имеющий доступ к `:65432` может получить дамп горутин, раскрывающий темы и внутреннее состояние. Порт также использует тот же адрес `host`, что и клиентский порт: по умолчанию `0.0.0.0`, то есть все интерфейсы. Отдельного адреса для профилирования нет. Не задавайте `prof_port` при эксплуатации либо ограничьте доступ межсетевым экраном или сетевой политикой. Предпочитайте системную учётную запись: запрос защищён обычной аутентификацией `$SYS`.

**Включение `prof_port` требует перезапуска.** Параметр не перечитывается, поэтому его включение на работающем узле означает последовательный перезапуск кластера. Во время инцидента это неудобно: искомое состояние может исчезнуть. Сначала используйте `nats server request profile`: команда не меняет конфигурацию, не требует перезапуска и снимает текущее состояние узла.

**Профиль блокировок пуст, пока сбор не включён.** Запрос `block` без настройки `prof_block_rate` возвращает пустой профиль: среда выполнения собирает блокировки только при ненулевом значении. В отличие от `prof_port`, `prof_block_rate` *можно* перечитать: увеличьте его через SIGHUP, снимите профиль и верните ноль. В остальное время оставляйте сбор выключенным — он замедляет сервер.

## Что уже готово {#where-you-are}

Теперь вы умеете снимать профиль работающего сервера. Кластер `east` и нагрузка ORDERS продолжают работать как прежде. У вас появился способ ответить на вопрос, недоступный четырём предыдущим источникам: если `/varz` сообщает расход памяти или CPU узлом `n1-east`, профиль показывает, на что именно расходуются ресурсы.

Есть два пути. `nats server request profile` работает через системную учётную запись на живом кластере, не требует изменений конфигурации и ограничивает профиль CPU 15 секундами. `prof_port` предоставляет все конечные точки `pprof` по HTTP без ограничения длительности и без аутентификации; для включения нужен перезапуск. Оба способа создают файлы для `go tool pprof`.
