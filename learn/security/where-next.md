# Куда двигаться дальше {#where-to-go-next}

TLS, сертификат клиента и шифрование диска закрыли оставшиеся пробелы ORDERS. Соберём модель и ссылки за пределами главы.

## Общая картина {#the-whole-model-in-one-picture}

Каждая составляющая отвечает на вопрос:

- **Учётная запись**: чей трафик? ORDERS и ANALYTICS имеют разные темы.
- **Пользователь**: кто подключён? Личность доказывается до входа.
- **Права**: куда можно публиковать и подписываться? Allow order-svc ограничивает orders.>.
- **TLS**: защищён ли канал? MTLS также задаёт личность сертификатом.

Согласованные экспорт и импорт пропускают только orders.shipped, сохраняя остальные границы.

Ответы на четыре вопроса определяют защищённость соединения; остальное — настройка этих ответов.

## Два ответа на вопрос о личности {#the-two-ways-to-answer-who-are-you}

Мир двух записей намеренно построен дважды.

**Централизованный** список в конфигурации проверяет данные напрямую. Правка и `nats-server --signal reload` без рестарта подходят небольшому набору пользователей.

**Децентрализованная** цепочка оператор — запись — пользователь убирает список с сервера. Команды выдают свои данные без серверной правки, что подходит множеству арендаторов.

Во время работы одинаковы личность, запись и права; различается источник доверия.

Третий способ — [auth callout](/learn/security/auth-callout) во внешнюю систему. [Карта главы](/learn/security/) помогает вернуться к части.

## Справочник {#reading-the-reference}

Здесь рабочие примеры, а полные шифры, JWT-поля и экспортные параметры оставлены отдельно.

Генерируемый [справочник](/reference/) даёт протокол, типы и стандарты. Глава объясняет связи, справочник — точную настройку.

## За рамками {#what-this-chapter-did-not-cover}

Четыре продолжения одиночного сервера:

**Несколько серверов.** У кластера, листа и шлюза собственные аутентификация и TLS. См. [Кластеризацию](/learn/clustering), [TLS](/reference/config/tls).

**Листовые узлы.** Периферия входит в центр через границу доверия с изученными [записями](/learn/security/accounts-and-multitenancy) и [учётными данными](/learn/security/decentralized-auth). Размещение их в leafnodes — в [Листах](/learn/topologies/leaf-nodes).

**Защита развёртывания.** Права файлов, системный доступ и квоты арендаторов — [Защита системы](/learn/deployment/hardening).

**Хранимое JetStream.** [Шифрование диска](/learn/security/encryption#encryption-at-rest) защищает доступ; [репликация](/learn/jetstream/surviving-node-loss) обеспечивает наличие данных после отказа. Это разные задачи.

## Что уже готово {#where-you-are}

Вы построили две схемы ORDERS, общий экспорт одной темы и внешний auth-сервис, понимаете запись, пользователя, права и TLS.

После учебных экспериментов остановите сервер, удалите временные конфигурации, сертификаты, хранилище JetStream и изолированное XDG_DATA_HOME либо оператора ACME из стандартного хранилища [режима оператора](/learn/security/operator-mode).

Ссылки выше расширяют модель к нескольким серверам и эксплуатации.

## Контрольный список перед эксплуатацией {#production-checklist}

Действия из типичных ошибок:

### Основы аутентификации — см. [Типичные ошибки](/learn/security/authentication-basics#pitfalls) {#authentication-basics--see-pitfalls}

- [ ] Отклоняйте анонимный вход списком пользователей.
- [ ] Храните bcrypt, не открытые пароли.
- [ ] Секреты вне git, через хранилище и .gitignore.
- [ ] Учётные данные в контексте, не URL.

### Авторизация — см. [Типичные ошибки](/learn/security/authorization#pitfalls) {#authorization--see-pitfalls}

- [ ] Запрашивающему разрешён `_INBOX.>` для ответов.
- [ ] Используйте шаблон реального пространства.
- [ ] Не выдавайте глобальный >.
- [ ] При пропусках проверяйте deny широких подписок.

### Учётные записи — см. [Типичные ошибки](/learn/security/accounts-and-multitenancy#pitfalls) {#accounts-and-multitenancy--see-pitfalls}

- [ ] No_auth_user только узкому пользователю.
- [ ] SYS с пользователем и system_account: SYS.
- [ ] Общие темы только через экспорт/импорт.

### Межаккаунтный обмен — см. [Типичные ошибки](/learn/security/cross-account#pitfalls) {#cross-account--see-pitfalls}

- [ ] Согласуйте обе стороны: отсутствующий экспорт ломает запуск, отсутствующий импорт молчит.
- [ ] Stream для одностороннего, service для request/reply.
- [ ] Подписывайтесь на локальное переименованное имя.

### Режим оператора — см. [Типичные ошибки](/learn/security/operator-mode#pitfalls) {#operator-mode--see-pitfalls}

- [ ] Account push после каждой правки, отзыва или смены signing keys.
- [ ] Системная запись обязательна resolver.
- [ ] Creds с 0600, без образов, журналов и git.
- [ ] Отслеживайте истечение.

### Децентрализованная аутентификация — см. [Типичные ошибки](/learn/security/decentralized-auth#pitfalls) {#decentralized-authentication--see-pitfalls}

- [ ] Офлайн-копия: `nats auth operator backup ACME acme-operator.backup`.
- [ ] На сервере только публичный operator JWT.
- [ ] Scoped signing keys вместо корневого seed.
- [ ] Осознанный срок `nats auth user credential order-svc.creds order-svc ORDERS --expire 720h` и план продления.

### Auth callout — см. [Типичные ошибки](/learn/security/auth-callout#pitfalls) {#auth-callout--see-pitfalls}

- [ ] Несколько auth-svc и настроенный timeout.
- [ ] Только auth-svc в auth_users.
- [ ] Отдельная запись и xkey для секретов.

### Шифрование и TLS — см. [Типичные ошибки](/learn/security/encryption#pitfalls) {#encryption--tls--see-pitfalls}

- [ ] Verify или verify_and_map для сертификата клиента.
- [ ] Личность сертификата из openssl x509 -noout -subject совпадает с пользователем.
- [ ] TLS также кластерам, листам и шлюзам.
- [ ] Сертификат узла с serverAuth и clientAuth.
- [ ] TLS-first сначала с `handshake_first: "300ms"`, затем true.
- [ ] Ротация до истечения плюс nats-server --signal reload.
- [ ] Ключ JetStream через `key: $JS_KEY`, prev_key лишь на один переходный рестарт.
