# Листовые узлы {#leaf-nodes}

У Acme работает суперкластер `east` и `west`, связанный шлюзами. Оба облачных региона контролируются компанией, ORDERS взаимодействует между ними.

Следующая площадка — цех, чьи машины публикуют `orders.*`. Заводская сеть за межсетевым экраном не принимает входящих подключений из интернета, а может лишь обращаться наружу.

Шлюз соединяет кластеры с доступными входящими слушателями и здесь не подходит. Для такого ограничения предназначен листовой узел. Распространение интереса и привязка учётной записи — части этой топологии.

## Что такое листовой узел {#what-a-leaf-node-is}

**Листовой узел** — сервер NATS, открывающий *исходящее* соединение к удалённой системе и передающий через него интерес к темам.

Сервер цеха подключается к `east`, а не наоборот. Достаточно одного исходящего соединения: входящие правила и публичный адрес цеху не нужны.

Удалённая сторона — **центральный узел** (hub), здесь кластер `east`. Листовой узел — `factory-1`.

Для местных машин `factory-1` — обычный NATS. Они публикуют `orders.created` без специальных настроек листового соединения.

Когда подписчик центральной системы запрашивает `orders.>`, интерес передаётся вниз, а подходящие заводские сообщения идут вверх. При местной подписке трафик центра идёт вниз. Переносятся лишь темы с интересом на другой стороне. Листовая связь расширяет обычное распространение интереса на один исходящий переход; внутренние маршруты и репликация разобраны в [Кластеризации](/learn/clustering).

Форматы интереса и сообщений описаны в [Справочнике → Протокол листовых узлов](/reference/protocols/leafnode). Здесь нужны конфигурация и поведение связи.

## Центральная сторона: приём листовых соединений {#the-hub-side-accept-leaf-connections}

На каждом сервере `east` добавьте `leafnodes {}` с адресом `listen`.

Стандартный порт — `7422`, отдельный от клиентского 4222, маршрутного 6222 и шлюзового 7222.

Конфигурация `n1-east` с новым блоком `leafnodes`:

```conf
# n1-east.conf — the east cluster config, now accepting leaf connections
server_name: n1-east
listen: 127.0.0.1:4222

jetstream {
  store_dir: "./js/n1-east"
}

cluster {
  name: east
  listen: 127.0.0.1:6222
  routes: [
    nats://127.0.0.1:6223
  ]
}

# NEW: accept inbound leaf node connections on 7422
leafnodes {
  listen: 127.0.0.1:7422
}
```

Добавьте блок и в `n2-east`, `n3-east`. На одной машине используйте 7423 и 7424. Листовой узел может выбрать любой центральный сервер, поэтому несколько адресов обеспечивают переподключение.

## Листовая сторона: исходящий remote {#the-leaf-side-dial-out-with-a-remote}

Вместо приёма листовых соединений `factory-1` задаёт **remote** — центральную систему назначения.

Запись находится в `leafnodes.remotes`, обязательное поле `urls` указывает адреса:

```conf
# factory-1.conf — a leaf that dials the east cluster
server_name: factory-1
listen: 127.0.0.1:4300

leafnodes {
  remotes: [
    {
      urls: [
        "nats://127.0.0.1:7422"
        "nats://127.0.0.1:7423"
        "nats://127.0.0.1:7424"
      ]
    }
  ]
}
```

У `factory-1` нет `cluster {}` и `gateway {}`. Это самостоятельный сервер с одним исходящим каналом в Acme. Его клиентский порт `4300` отдельный от центрального.

`urls` указывают листовые порты всех центральных серверов, давая запас при отказе.

Листовой узел не ограничен одним центром: список `remotes` может подключать разные системы NATS. Он также может открыть собственный `leafnodes { listen }` и принимать более удалённые узлы: связи образуют деревья.

При эксплуатации remote обычно содержит `credentials` для подтверждения личности и `account` для выбора учётной записи. Пока используем запись по умолчанию; к этим полям вернёмся в [эксплуатационном уровне учётных записей](#accounts-the-production-layer).

## Учётные записи: эксплуатационный уровень {#accounts-the-production-layer}

Демонстрации достаточно записи по умолчанию без аутентификации. При эксплуатации нагрузки изолируют **учётными записями**, каждая из которых задаёт отдельное пространство тем. Для связи remote нужны поля:

- `account` выбирает локальную учётную запись листового узла.
- `credentials` указывает `.creds`, подтверждающий личность перед центром, который выбирает соответствующую запись у себя.

Согласовав записи на концах, цех и облако получают общее изолированное пространство тем. Создание записей, выпуск данных и разрешение листовых соединений рассмотрены в [Безопасности](/learn/security). Здесь остаётся запись по умолчанию.

## Местные клиенты скрыты за листовым узлом {#local-clients-stay-hidden-behind-the-leaf}

Машина подключается к `factory-1` обычным клиентом и не появляется отдельным соединением в центре. Там видно лишь листовое соединение `factory-1`.

Сто или тысяча дополнительных машин не меняют этого: центральная сторона взаимодействует с одним листовым узлом.

Связь передаёт *интерес*, не раскрывая клиентов. Подписчик центра на `orders.>` получает заводские заказы, не зная числа машин и даже их расположения за листом.

Соединения и темы следует различать. Приватность заводской темы определяется привязанной учётной записью. Отдельная запись ограничивает обмен импортом и экспортом — это **изоляция пространства адресов**, решение уровня [учётных записей](#accounts-the-production-layer), а не автоматическое свойство канала. В записи по умолчанию границы тем нет; интерес проходит как по маршрутам кластера.

## Передайте сообщение через листовую связь {#send-a-message-across-the-leaf-link}

Запустите центр и лист, подпишитесь в цехе, опубликуйте в центре. Сообщение пойдёт от центра к листу.

В отдельном терминале подпишитесь на `orders.>` через `factory-1`:

```bash
nats sub "orders.>" --server nats://localhost:4300
```

В другом опубликуйте через `east`:

```bash
nats pub orders.shipped "order ord_8w2k shipped" --server nats://localhost:4222
```

Заказ приходит в цех:

```
[#1] Received on "orders.shipped"
order ord_8w2k shipped
```

Лист передал интерес `orders.>` вверх, центр направил подходящее сообщение вниз по единственному соединению.

## JetStream через листовой узел {#jetstream-over-a-leaf}

Если `factory-1` запускает собственный JetStream с локальным ORDERS, ему нужен **[домен](/reference/config/jetstream/domain)**.

Домен — имя, разделяющее системы JetStream через листовую связь. Потоки цеха и центра остаются отдельными и адресуемыми; без разных доменов они конфликтуют.

Локальное зеркало `ORDERS` центра или сбор заводских данных в центральный поток разобраны в [JetStream → Зеркала и источники](/learn/jetstream/mirrors-and-sources). Здесь вводится только домен.

## Типичные ошибки {#pitfalls}

При первом подключении листа возникают две проблемы.

**Перепутанное направление соединения.** Лист подключается *наружу*. Центр слушает 7422, лист задаёт `remotes`. Если настроить слушатель в цехе и ждать подключения центра, ничего не произойдёт. На стороне только с исходящим доступом нужен `remotes`, на принимающей — `leafnodes { listen }`.

**Ожидание отдельного JetStream без домена.** Если `factory-1` включает JetStream и разделяет системную запись центра, он расширяет *центральную* систему. Созданный в цехе поток может оказаться в центре. Для отдельного локального хранилища задайте собственный домен; обмен данными описан в [зеркалах и источниках](/learn/jetstream/mirrors-and-sources).

## Что уже готово {#where-you-are}

Acme вышла к периферийным устройствам:

- Кластеры `east` и `west` связаны шлюзами.
- `factory-1` устанавливает исходящее соединение к `east` на 7422.
- Интерес `orders.*` передаётся в обе стороны в записи по умолчанию; при эксплуатации нужна именованная запись.
- Машины цеха — обычные местные клиенты, скрытые за листом и разделяющие пространство тем с облаком.

Pub/sub прежний: публикация машины в `factory-1` устроена как публикация в `n1` на странице [Отдельный сервер](/learn/topologies/single-server).
